**Subagents are OK on this project now, at least for read-only research.** Earlier in this project's history the user twice rejected an Agent tool call outright when it was used to plan a feature batch, so the standing rule became "do everything directly." That's since been reversed: 2026-08-18, the user said "You can use subagents if that would help usage" and later "You can subagents in future as long as its effective and efficient," and then explicitly confirmed using an Explore-type agent for a broad multi-file research sweep (surveying an existing plugin-migration pattern across ~10 files before a new migration) by not objecting and continuing the same request thread.
**Why:** the user's stance changed from a hard no to a conditional yes — "effective and efficient" is the bar, not blanket delegation.
**How to apply:** Read-only research/survey tasks spanning many files (e.g. "find every reference to X across the codebase and summarize the pattern") are good subagent candidates — use Explore or general-purpose for those. Stay more cautious about delegating actual planning or implementation decisions to a subagent unprompted; direct work is still the safer default there unless the user asks for delegation.

**Config schema changes always get a migration path, never a breaking change.** Every time the on-disk config shape changed (e.g. `ch.folder` string → `ch.folders` array, `ch.commercialsEnabled` boolean → `ch.commercials` object), a `normalizeChannel()`-style migration was added and verified against the user's real saved config, so existing channels/settings survive the upgrade with zero data loss.
**Why:** the user has a real, large config (13 channels, hundreds of scanned video files with per-file metadata) built up over the life of this project — losing or corrupting it on a schema change would be costly and was treated as unacceptable throughout.
**How to apply:** Any time a feature requires changing the shape of `S.config` or a channel/block object, write the migration first, and verify it end-to-end against a backed-up copy of the real config (see [[retro-cable-box-architecture-constraints]]) before considering the feature done.

**The user drives feature scope tightly, one feature (or a small named batch) at a time, and expects genuine design forks surfaced via AskUserQuestion rather than guessed at.** Requests are typically short and specific ("add multi-folder support for channels," "also implement ability to add audio to channels 1 and 2"); when there's a real fork in approach (e.g. how granular per-channel/per-block ad overrides should be), it's better to make a reasoned scoping call and state it plainly than to either over-build every possible axis of configurability or silently under-scope.
**Why:** observed pattern across many features in this project — the user answers AskUserQuestion prompts decisively when asked, and has not pushed back on reasonable scoping calls stated explicitly (e.g. "leaving dayparting blocks unchanged for now" was accepted without objection).
**How to apply:** Don't preemptively gold-plate a feature with every adjacent capability; implement what was asked, state any scope decisions made along the way, and let the user ask for more if they want it — which they routinely do in follow-up messages.

**When a fix is "make this cosmetic effect less intense," check first whether it should be a persistent slider instead of a hardcoded value tweak.** 2026-08-05: asked to tone down the CRT flicker effect, applied a one-off CSS value change; the user's immediate follow-up was "or make it a slider with more options?" — turning it into a fourth CRT-intensity slider (alongside the existing SCANLINES/VIGNETTE/GRAIN ones) was the better answer from the start, matching a pattern already established elsewhere in the app (static-burst intensity, picture-mode presets, etc. are all user-configurable, not fixed).
**Why:** this app already exposes most cosmetic/effect intensities as sliders in the DISPLAY settings tab — a fixed-value tweak to an existing effect is the exception, not the norm, for this codebase.
**How to apply:** Before hardcoding a new value for an existing visual/audio effect's intensity (as opposed to fixing an actual bug), check whether a sibling slider/config pattern already exists for similar effects on the same screen — if so, default to adding a slider rather than picking a fixed number, even if the user's initial phrasing sounds like a one-off ("tone it down").

**Never `git commit` in either repo (original or [[retro_cable_box_foss_repo]]) unless explicitly told to.** 2026-08-18: made an initial commit in the new FOSS repo as part of "init a private git repo" — reasonable at the time, but the user immediately said "I want to tell you when to commit" and had the commit removed from history (`git update-ref -d HEAD`, safe for a root commit — keeps the working tree/index intact).
**Why:** the user wants to control commit timing themselves, even during active multi-file work sessions where a commit might otherwise seem like a natural checkpoint.
**How to apply:** Stage and edit freely, but never run `git commit` (in either repo) without an explicit instruction in that turn — "let's commit," "commit this," etc. Finishing a feature or reaching a good checkpoint is not itself permission.

**Once retro-cable-box-foss's touched files are confirmed byte-identical (via `diff`) to the already-CDP-verified retro-cable-box files, don't also boot-test FOSS separately.** 2026-08-17: after CDP-verifying a PLUGINS tab redesign in the main repo and then copying the same files into FOSS, started a second full CDP boot-test pass on FOSS — the user interrupted ("If FOSS is synced then theres no need to verify test"). A `diff` confirming the copied files are exactly identical to the versions already exercised live is sufficient; a second boot test of literally the same code is redundant work, not extra rigor.
**Why:** [[retro_cable_box_foss_parity]]'s hard rule is that core files stay byte-identical between the two repos — once that identity is verified by `diff`, there is no new code path in FOSS the main-repo test didn't already exercise. This is distinct from earlier sessions where FOSS-specific testing *was* warranted (e.g. verifying its distinct app identity/userData path, or a fresh-install-only behavior) — those are testing something FOSS-specific, not re-running an identical code path.
**How to apply:** After syncing files to FOSS, a `diff`-confirmed-identical check replaces a redundant CDP pass. Still do a real FOSS-specific test when the change involves something that could differ between the repos (app identity, first-run state, FOSS's own excluded-plugin set) — the shortcut only applies to genuinely identical, already-tested code.
