**One `<video>` element for everything, not one per use case.** All playback — real channel content, commercial bumpers, and virtual-channel (CH1/CH2) background audio — deliberately goes through the single `player` element (`renderer/js/dom.js`) rather than adding parallel `<video>`/`<audio>` elements per feature.
**Why:** a second element would need its own volume/mute/pause/power-off wiring duplicated across every existing control path (the `M` mute key, `+`/`-` volume, `powerOff()`, etc.). Reusing the one element means every new use of it inherits all of that for free. This is why virtual-channel audio was implemented by pointing `player.src` at an audio file with `player.loop = true` instead of a new `<audio>` element.
**How to apply:** Before adding a new place video/audio plays (PIP, a second window, simultaneous multi-channel preview), check whether it can still route through the single `player` element. If it genuinely can't (true PIP needs two simultaneous decodes), flag it explicitly as a bigger architectural fork rather than quietly bolting it on — that's what happened with the PIP-while-surfing idea, which got pushed to the lowest priority tier for exactly this reason.

**The app is fully offline/local — no network dependencies for content.** Everything is either the user's own local media files, synthesized (Web Audio SFX/tones, `speechSynthesis` for the EAS voiceover), or user-authored text (public-access bulletin slides).
**Why:** stated explicitly when scoping the weather-channel idea — it was deliberately kept to "text/generated, not a live API" to preserve this. The same reasoning ruled out AI-generated episode blurbs as a feature (would require an external LLM call for something currently free/instant/offline).
**How to apply:** When a feature idea would naturally reach for a live external API or an LLM call (weather data, episode synopses, etc.), default to a local/generated/user-authored substitute instead, and call out the tradeoff explicitly rather than silently adding a network dependency.

**Every risky change gets a real Electron boot test against the user's actual saved config, not just static checks.** The established pattern: `node --input-type=module --check < file.js` per touched renderer module (plain `node -c` fails on ESM import/export syntax since the project has no `"type": "module"` in package.json) + a static import/export graph checker + an un-namespaced-shared-state sweep, THEN a real `electron <script>` boot that drives the actual UI via dispatched keyboard events and reads back real DOM/state. The real config file is always backed up (`cp channels.json channels.json.bak-...`) before any test that might trigger a debounced autosave, and restored + the backup deleted immediately after.
**Why:** static checks alone missed real bugs during the module-split refactor (a spread-operator edge case, missing imports) that only the real boot test caught. The user's config is real production data (13 channels, real media paths) — not a throwaway fixture — so it must never be left mutated by a test run.
**How to apply:** For any change touching config schema, playback timing, or cross-module wiring, don't declare it done from code review or unit tests alone — run it in the real app against the real config with the backup/restore discipline above. **Gotcha confirmed 2026-08-04:** `app.setPath('userData', ...)` pointed at the real `%APPDATA%/retro-cable-box` folder is not optional/defensive — it's required. Running `electron <bare-script.js>` (as opposed to `electron .`) makes Electron pick a different default app name/userData dir, so without the explicit `setPath` call the boot test silently loads an empty/fresh config instead of the real one (looks like a normal boot — 1 fresh channel, setup screen — nothing errors, it just isn't testing anything real). Confirm you're against the real data by checking channel count in the loaded config before trusting any other result. Dynamic `import('./js/state.js')` inside `webContents.executeJavaScript` returns the *same live module instance* the app's own `<script type="module">` already loaded (ESM module cache is keyed by resolved URL) — this is a convenient way to read/call real app state (`S`, `tuneToChannel`, etc.) directly from a driver script instead of only simulating key presses. **Gotcha confirmed 2026-08-04 (session 2):** the CDP driver approach that works for testing this app is `electron . --remote-debugging-port=<N> --remote-allow-origins=*`, attach over `ws://127.0.0.1:<N>/json/list`'s `webSocketDebuggerUrl`, then drive via `Runtime.evaluate` (dispatch real `KeyboardEvent`s, or `await import('./js/state.js')` for live state) — this is a lighter, Windows-native alternative to the Playwright/xvfb pattern the generic `run` skill defaults to, which doesn't apply here (this is a real Windows desktop with a display, not headless Linux CI). `window.confirm()`/`alert()` ARE interceptable this way, via `Page.enable` + handling `Page.javascriptDialogOpening` with `Page.handleJavaScriptDialog`. **What is NOT drivable this way:** anything exposed through `preload.js`'s `contextBridge.exposeInMainWorld('api', ...)` — that object is frozen (`writable:false, configurable:false` on every property) from the renderer's own JS, so attempting to stub/monkeypatch `window.api.someMethod` for a test silently no-ops (no throw in sloppy-mode eval) and the REAL handler still fires. This bit hardest on `dialog.showSaveDialog`/`showOpenDialog`-backed features (config export/import): the stub attempt silently failed, the real native OS file dialog opened for real and hung waiting on a human that isn't there, and had to be dismissed by killing the electron process tree. For any feature behind a native OS dialog, don't attempt to drive it via CDP — verify the IPC plumbing via a channel-name cross-check (`grep ipcMain.handle` vs `grep ipcRenderer.invoke`) plus an isolated Node script that exercises the exact same file-I/O/validation logic against scratch files, and say plainly that the dialog interaction itself needs a quick manual click-test.

**The `S.config.theme` (digital-2000s/analog-90s) token override now applies box-wide via `html[data-theme]`, not just `#tv-screen[data-theme]`.** Originally (2026-08-04, session 3) it was deliberately scoped to `#tv-screen` only, "so the setup/admin screen never re-skins." On 2026-08-04 (session 4) the user explicitly asked for the opposite — the settings screen wasn't "reflecting the current theme," meaning they wanted the whole app re-skinned, not just the TV screen — confirmed via AskUserQuestion before implementing. `applyTheme()` in `themes.js` now sets `document.documentElement.dataset.theme`, `tokens.css`'s override block selector is `html[data-theme="analog-90s"]`, and the handful of element-specific per-era rules in `overlays.css` (power-fx line animation, channel-entry digit plate) became `html[data-theme="analog-90s"] #tv-screen ...` instead of `#tv-screen[data-theme="analog-90s"] ...`. `showSetupScreen()` and `showTvScreen()` (`app.js`) both call `applyTheme()` now so either entry point re-skins immediately.
**Why:** this was a genuine design fork (two very different meanings of "settings screen not updating to reflect current theme" — a stale dropdown value vs. the setup screen's own colors never reacting) and the user's answer reversed the prior explicit scoping decision. Don't assume the old `#tv-screen`-only scoping is still current without checking `tokens.css`/`themes.js`.
**How to apply:** Any new per-era CSS override (a third theme, a new themed element) should target `html[data-theme="..."]` (optionally narrowed with a descendant selector like `#tv-screen` or `#setup-screen` for element-specific rules), not `#tv-screen[data-theme="..."]` directly — that selector no longer exists.

**(Superseded 2026-08-05 — kept for history) The old box-wide "COMMERCIAL BREAKS" toggle bumper-pool-gating behavior no longer exists.** As of the tagged-interstitials rewrite (see [[retro-cable-box-overview]]), `ch.commercials`/`block.commercials`/`S.config.commercials` no longer have `folder`/`files`/`useOwnFolder` at all — bumper *content* now lives in one shared `S.config.interstitials.pool` (tagged by `channelAffinity`/`blockAffinity`), and `commercials` objects are purely "when/whether" (`enabled`/`timing`/`intervalMinutes`). The box-wide `commercials.enabled` checkbox was removed from the UI entirely since it had no remaining role once the shared-pool-vs-own-folder distinction went away. If you see references to `useOwnFolder`/`bumperPoolFor`/a box-wide "COMMERCIAL BREAKS" checkbox anywhere, they're stale — check `renderer/js/interstitials.js` instead.

**Every "when does X happen" system on this app must be a deterministic pure function of `viewNow()`, not an event-timer with `Math.random()`.** Established with `resolveActiveSource`/`computeSourcePosition` (`schedule.js`) for content, extended 2026-08-05 to breaks (commercials/station-ID/trivia/up-next idents) via `resolveBreakAt(ch, atMs)` in `interstitials.js`. The old commercial/station-ID/trivia systems each used a real `setTimeout` armed for a random-ish interval and picked bumpers with `Math.random()` at the instant the timer fired — meaning "what's airing" wasn't a function of time at all, just of when you happened to be watching. `resolveBreakAt` fixes this: break *timing* is computed from a slot formula anchored to the content source's own anchor (`intervalSlot`/`boundarySlot`), and break *selection* uses a seeded weight-expand-then-shuffle-per-cycle scheme (`pickDeterministic`, a small djb2-hash-seeded mulberry32 PRNG) instead of `Math.random()` — same `(pool, seedKey, slotIndex)` always yields the same pick, whether `slotIndex` maps to a moment in the past or the future. This is what makes the time-machine VCR-shuttle preview able to show "what commercial would be/was airing" at any scrubbed instant, consistent with what live playback actually shows there — both call the exact same `resolveBreakAt`.
**Why:** the user explicitly asked for the time machine to "remember" past/future commercials, which is only possible if break state is derivable from a timestamp alone, with no hidden mutable history to store or desync.
**How to apply:** Any new scheduled/recurring on-screen event (the still-unbuilt spec phases: promo lead-time bumpers, dynamic/templated up-next overlays, premiere jingles, mid-video `everyNMinutes` breakpoints) should be built the same way — a pure `resolve*At(ch, atMs)` function, no `setTimeout`-scheduled randomness — and should reuse `pickDeterministic`/`intervalSlot`/`boundarySlot` rather than inventing a new selection mechanism. Live-playback triggering still uses `setTimeout`, but only to know *when* to next call the resolver (`nextBreakBoundary`) — the decision itself is always freshly computed, never cached across the timer firing.

**CDP boot-test gotcha (2026-08-05): a migration's autosave landing in the real config during a boot test is correct, not test pollution — but scratch data you added for the test is not, and must be explicitly popped before the script returns.** Confirmed twice this session: loading the real config through updated `normalizeChannel`/`applyConfigDefaults` migration code, then letting the app's normal debounced autosave fire, persists the *migrated* shape to the real `channels.json` — that's the actual intended outcome of a schema-migration feature landing, not a side effect to revert. Separately, any channels/pool-entries/blocks you construct in-memory purely to exercise a code path (e.g. a scratch channel number like `9001` used to test `resolveActiveSource`) are NOT part of that deliverable and will get swept into the same autosave if left in `S.config` — one instance this session left a real block's `mode` mutated by a UI smoke-test click that landed on the wrong element (see `channels.js` `ch4` block), caught only by a follow-up read-back diff against the pre-test backup.
**How to apply:** Still always back up `channels.json` before a boot test (per the existing CDP discipline above). After the test, diff the live file against the backup: a diff that's exactly the intended schema migration (and nothing else) is success, not something to revert; a diff containing scratch/test-only entities means cleanup was missed — go remove them from `S.config` before the process exits (or the next autosave) rather than restoring the whole file from backup, which would also discard the real migration you were trying to verify actually landed.

**Bug that slipped through despite a thorough boot test (2026-08-05): verifying a resolution engine's backend logic via CDP is not the same as verifying the setup-screen UI that edits it — the two need separate passes, and only clicking real DOM elements catches missing-import bugs.** The tagged-interstitials phase shipped with `renderInterstitialsList()` (`setup.js`) calling `sortedChannels()` without importing it from `channels.js` — a plain `ReferenceError` on the very first render. This was invisible to the whole boot-test pass in that phase because every check called `interstitials.js` functions directly (`resolveBreakAt`, `nextBreakBoundary`, migration helpers) and never actually opened the setup screen / clicked the new PROGRAMMING-tab controls — so a function that's perfectly correct in isolation still shipped broken because the thing that *calls* it (a `<select>`'s render loop) had a bug the backend tests couldn't see. The user caught it immediately ("add entry in programming does nothing") since the pool already had 2 real entries, so the very first render after opening settings threw. Reproduced and fixed via `document.getElementById(...).click()` on the real button (not a re-implementation of the click handler) plus `window.onerror` capture, which is the reliable way to catch this class of bug — calling the exported function directly instead of `.click()`-ing the element would have masked the same problem another way (right function, wrong wiring).
**How to apply:** Whenever a phase adds or changes setup-screen UI (a new panel, a new list editor, a new button), the boot-test pass must include at least one `element.click()`/`dispatchEvent('change')` per new interactive control, with `window.onerror` (or an exceptionDetails check on the CDP `Runtime.evaluate` result) capturing thrown errors — not just calling the underlying data/resolution functions directly. Do this in addition to, not instead of, the pure-function backend checks.

**CDP UI-click tests on this app's setup screen will silently hit the wrong row/block when more than one exists, because rows share identical button/label text (`document.querySelectorAll('button').find(b => b.textContent === 'DATE RANGE')` finds the FIRST one in the DOM, not "the one I just added").** Confirmed twice now: once mutating a wrong block's mode during the blocks-unification phase (caught immediately by a targeted re-check), and again during the interstitials phase's UI smoke test, where a scripted click sequence (ADD BLOCK → click "DATE RANGE" → switch mode to daily → add a day override) landed on channel 4's real pre-existing Christmas block instead of the newly-added scratch block, because that channel already had one block and the "DATE RANGE" button lookup matched the *existing* block's toggle first. A cleanup filter then correctly-per-its-own-logic deleted "the dateRange+daily block with dayOverrides" — which by then was the *real* one, not the scratch one — leaving a stray empty scratch block behind in memory. Caught only because a follow-up read-back showed a `dayOfWeek` block where a `dateRange` block should have been; the on-disk file was still correct at that point (no autosave had fired), so an in-memory repair (not a disk restore) fixed it.
**Why:** every block/row-list editor in this app (SCHEDULE blocks, day overrides, the interstitials pool) renders N structurally-identical rows with the same control labels — there is no unique per-row selector to grab by text content once N > 1, and test scripts that assume "the first match is the one I just touched" will occasionally be wrong on a channel that already has data.
**How to apply:** When UI-testing a list/row editor on a channel or scratch object that might already have entries, either (a) test against a freshly-created scratch channel/object with zero pre-existing rows so "first match" is unambiguous, or (b) scope the element query to the specific row (e.g. `list.children[list.children.length - 1]` right after an add, or track the row element returned by a prior targeted query) rather than a bare document-wide text match. After any such test touching real channels, always read back and diff the specific object touched (not just a pool/count size) before considering the test clean — a count matching doesn't prove the *right* object was touched.
**Extended 2026-08-05 (session 5, volume-settings QOL pass):** the same wrong-target risk applies *within* a single row, not just across rows — a selector like `input[type="checkbox"]:last-of-type` scoped to a shared parent class (e.g. every `.channel-options label.shuffle-toggle`) matches the *first* checkbox in DOM order across every such label, not "the last one added to the row." This actually hit a real channel: testing a new per-channel VOLUME-override checkbox this way instead grabbed the pre-existing SHUFFLE checkbox on real channel 4, checking it and triggering its correct-but-destructive existing side effect (`if (ch.shuffle) shuffleArray(ch.files)`), permanently reshuffling ~228 real files. Caught by the routine post-test diff (way too large to be the intended schema migration) and fixed by restoring from the pre-test backup, then re-scoping the selector by exact label text (`Array.from(...).find(l => l.textContent.trim() === 'OVERRIDE')`) instead of position/type. Separately, in the same session: a scratch channel tuned to (`tuneToChannel(9201, ...)`) and then deleted left `S.config.lastChannel = 9201` behind when the process was killed before tuning back to a real channel — a dangling reference to a since-deleted channel that the next autosave persisted right alongside the actual intended schema migration. Caught the same way (post-kill diff review), hand-fixed with a one-line Node script (`JSON.stringify(config, null, 2)`, matching main.js's own save format) rather than a full restore, since the real migration in that same autosave needed to survive.
**How to apply (extended):** (1) When targeting one specific control within a row that has several controls of the same tag/type (multiple checkboxes, multiple selects), scope by exact visible label text or another attribute unique to that control, never by DOM position (`:last-of-type`, `:nth-child`) or bare tag/type — those describe "which slot in the row," not "which control." (2) Before ending a test that tuned to / interacted with a scratch channel number, either tune back to a real channel or verify `S.config.lastChannel` (and any other single-value field that could reference a scratch id) isn't left pointing at it — the post-test diff check must cover config-wide singleton fields, not just the array/pool the scratch object was added to.

**CSS transitions on large overlay panels over the live `<video>` need `will-change: transform, opacity` and must never share a frame with a forced synchronous reflow.** The docked/full-page guide-grid open/close animation (2026-08-04, session 4) made video playback visibly stutter. Two causes, both fixed: (1) `.guide-grid` had a gradient background + blurred `box-shadow` but no compositor-layer hint, so the browser re-rasterized it every animation frame instead of just re-compositing a GPU layer — fixed by adding `will-change: transform, opacity` to `.guide-grid` in `guide.css`. (2) `openGuideGrid()` (`guide.js`) ran the heavy `renderGuideGrid()` DOM rebuild and then forced a synchronous layout via `void guideGrid.offsetWidth` in the same tick as starting the animation — classic layout-thrashing landing exactly when smooth frames were needed. Fixed by replacing the forced-reflow trick with a double nested `requestAnimationFrame` before adding the `.open` class (the standard robust way to guarantee a starting state is painted before triggering a transition, without forcing sync layout).
**Why:** confirmed via a real CDP frame-timing test (dispatch the rAF loop that opens/closes the guide, record 40 `requestAnimationFrame` timestamp deltas) — before the fix the animation would even fail to settle in some conditions; after, deltas were rock-solid ~6.9-7.1ms with zero spikes on both open and close.
**How to apply:** Any new animated overlay that sits over `#player` (the video) should get `will-change` on the animated properties, and its JS trigger must not do heavy DOM rebuilds + forced layout reads in the same tick it flips the class that starts the transition — defer the class flip via double-rAF instead.

**Extended 2026-08-05 (session 6) — the guide-freeze fix above was only a partial mitigation (deferred *when* the expensive rebuild ran); the full fix reduces *how much* runs synchronously.** `renderGuideGrid()` (`guide.js`) still called `getChannelSchedule()` for every channel on every open even after the `setTimeout(0)` deferral — with 70+ channels that's still ~108ms of synchronous work, just moved one task later. The real fix: render only enough real-channel rows to cover the current viewport synchronously (`Math.max(S.guideSelRowIdx + 1, S.guideDocked ? 6 : 24)`, so the selected row is always included for the immediate scroll-into-view/info-panel update), then fill in the rest via `scheduleRemainingRows` — chunked `setTimeout(0)` passes of `GUIDE_ROW_CHUNK_SIZE` (12) channels each. A render-generation counter (`S.guideRenderGen`, bumped at the top of every `renderGuideGrid()` call) guards the chunked continuation: if a newer render has started (filter change, the 30s tick refresh, dock-mode toggle) before an in-flight chunk pass finishes, the stale pass checks its captured `renderGen` against the current one and stops appending instead of racing the newer render's rows into the grid.
**How to apply:** Any other place in this codebase that renders a per-item list where each item's row costs real computation (not just DOM construction) — a future "cross-channel calendar overview," a per-file transcode-status list, etc. — should follow the same shape: render a viewport-covering + selection-covering synchronous batch first, chunk the rest via `setTimeout(0)`, and guard chunked continuations with a render-generation counter so a superseded render's stale chunks can't corrupt a newer one.

**Gotcha confirmed 2026-08-05 (same session): a fixed "how many rows to render synchronously" cap is wrong when it doesn't scale with the actual list size — it can make small, cheap lists *worse* by turning a one-shot render into a visible multi-frame pop-in.** The first version of the above chunking fix capped the initial synchronous batch at `docked ? 6 : 24` unconditionally. The user's real channel list is only 13 — nowhere near the 70+ that motivated chunking in the first place — so that cap still applied, and rows started visibly growing in over several frames while the slide-open CSS transition was still playing, a new artifact that hadn't existed before (the pre-fix code rendered the whole list in one synchronous shot, just deferred by one `setTimeout(0)` tick). The user caught this by re-reporting the shake was still there after the fix landed and floating "could be the guide animation" as a hypothesis — which turned out to be exactly right. Fixed by adding a size threshold (`GUIDE_LAZY_FILL_THRESHOLD`, 30): lists at or under it render atomically (all in the initial batch, no chunking at all), and only lists above it get the viewport-first + chunked-fill treatment. Confirmed via the in-page rAF-sampling technique (see above) that the real list now jumps straight from empty to fully populated in a single frame, while a synthetic 83-channel list still chunks.
**How to apply:** Any "render the visible slice now, the rest later" optimization needs its trigger threshold to be about *actual cost* (would rendering the whole thing right now be expensive?), not a blanket policy applied regardless of list size — check the threshold against the realistic small/common case, not just the large case the fix was written for, before calling it done. When a user says a perf/visual fix "still isn't fixed," don't only re-verify the original hypothesis (main-thread block) — check whether the fix itself introduced a *different* visible artifact.

**Final resolution (same session): after both JS-side perf fixes above, the user still reported the guide-open "shake" — the actual remaining cause was the guide grid's own CSS open/close transition, unrelated to either JS fix. Removed the animation outright rather than attempting a fourth perf-tuning pass.** `.guide-grid` had `transition: transform 240ms …, opacity 200ms …` plus `will-change`, with `guide.js`'s `openGuideGrid()`/`closeGuideGrid()` doing a double-`requestAnimationFrame` dance to sequence the transition's start and a `setTimeout(GUIDE_TOGGLE_ANIM_MS)` delay before actually hiding the panel on close. All of that is gone now: the panel shows/hides purely via the `.hidden` class (instant, no transition), `guide.css`'s `.docked`/`.full` variants no longer set a `transform`/`opacity` starting state, and the now-dead `GUIDE_TOGGLE_ANIM_MS` constant + `S.guideCloseTimer` field were deleted rather than left unused. Confirmed via the same in-page rAF-sampling technique used throughout this investigation: both `#player`'s and `.guide-grid`'s own bounding rects now jump directly between their hidden/settled states in a single frame, with zero intermediate transform steps, and frame timing stays flat (~7ms, zero spikes) through the whole open/close.
**Why:** three rounds of perf-only fixes (defer the rebuild, lazy-fill rows, then fix the lazy-fill's own regression) all targeted JS-side causes of main-thread blocking, but the user's repeated "still shaking" reports meant the actual cause was somewhere the JS fixes couldn't touch — a pure-CSS transition on the panel itself. When a user says a fix for a *visual* symptom "still isn't fixed" after you've addressed every JS-side hypothesis, check whether a CSS transition/animation on the affected element is the real (or an additional) cause before adding more JS-side mitigation — sometimes removing an animation is the right call over tuning it further, especially after multiple tuning passes haven't resolved it.
**How to apply:** If a future feature wants to reintroduce a slide/fade for this or a similar overlay, treat it as a new feature request requiring its own perf validation (frame-timing rAF sampling through the full transition, not just at rest) — don't assume the old transition timing/easing was safe just because it looked fine in isolation; it demonstrably wasn't once combined with a real 70+-channel schedule rebuild.

**Gotcha confirmed 2026-08-04 (session 4) — CDP-driven `requestAnimationFrame` testing needs `Page.bringToFront` first, or rAF silently never fires.** A window driven purely over the CDP WebSocket (dispatching synthetic `KeyboardEvent`s via `Runtime.evaluate`, no real OS-level focus) is still a backgrounded page as far as Chromium's rAF throttling is concerned — `requestAnimationFrame` callbacks can simply stop firing, which for the guide's double-rAF open animation meant the `.open` class never got added and the panel stayed invisible (translated off-screen) even though `hidden` was `false`. Sending `Page.bringToFront` (a plain CDP command, no extra tooling) over the same WebSocket before dispatching the interaction fixed it — frame timestamps then arrived at a rock-solid ~7ms cadence.
**How to apply:** Add [[retro-cable-box-architecture-constraints]]'s existing CDP driver recipe: call `Page.bringToFront` once after attaching, before any test that depends on `requestAnimationFrame`, CSS transitions, or anything else gated on page-visibility/focus state — not just for animation-timing tests, since the same throttling could mask other visibility-dependent bugs too.

**(Partial reversal, 2026-08-05 session 3) Live content playback is no longer a pure function of `viewNow()` — it now carries a small, explicit piece of state (`S.contentLostMs`) so a show pauses through a break and resumes where it left off, instead of skipping ahead by the break's length.** Asked directly via AskUserQuestion ("should the show resume exactly where it left off, or keep advancing through the break like real broadcast") and the user chose freeze-and-resume over the realistic-broadcast default. Implementation, all in `playback.js`: `computeLiveContentPosition(ch)` (replaces the old direct `computeLivePosition(ch)` call in `playChannelLive`) computes position from `viewNow() - S.contentLostMs` instead of raw `viewNow()`; `startBreak` timestamps `S.breakEnteredAtMs` whenever a break actually interrupts content (not for a text-only station-ID bar); `endBreak` credits `viewNow() - S.breakEnteredAtMs` back into `S.contentLostMs`. Break *timing itself* (`resolveBreakAt`/`nextBreakBoundary`/ad cadence) deliberately still runs on real `viewNow()` — only the content clock lags, not when breaks fire — so [[retro-cable-box-architecture-constraints]]'s existing "pure function of `viewNow()`" rule still fully applies to break resolution, just not to live content position anymore. `S.contentLostMs` is scoped by a composite `${ch.number}:${source.key}` key and auto-resets to 0 whenever that key changes (channel change, daily/weekly rollover, a new block becoming active), so lag never carries across a source it doesn't belong to.
**Why:** the previous design (`interstitials.js`'s "breaks don't consume timeline time" comment, written earlier the same day) was a deliberate choice to mirror real linear broadcast; the user reconsidered and wanted DVR-style resume instead. This is a genuine, user-directed architecture reversal, not a bug fix — don't "correct" it back toward the old pure-stateless model without checking with the user first.
**How to apply:** Any new code path that starts/resumes live playback (a new tune-in entry point, a new power-on path, etc.) must go through `playChannelLive`/`computeLiveContentPosition`, not call `computeLivePosition` from `schedule.js` directly, or it'll silently ignore accumulated break lag. Conversely, anything that needs the *schedule's* idea of "what's on now" regardless of real playback state (the EPG guide grid, the up-next banner's promo lookup, time-machine shuttle preview) should keep using the raw `computeLivePosition`/`resolveActiveSource` — those are deliberately unaffected, and mixing the two up would make the guide disagree with what's actually airing.

**Any state that only makes sense during continuous real-time live playback must be explicitly reset when a path diverges from real-time tracking (time-machine shuttle), not just left to go stale.** Found 2026-08-05 session 3: `startShuttle()` (`timemachine.js`) stopped the live break-boundary timer but never reset `S.activeBreakKey`/`S.activeBreakInterruptsContent`/`S.breakEnteredAtMs` — the shuttle preview (`updateShuttlePreview`) tracks break overlays entirely independently while scrubbing, so those fields just froze at whatever they were when shuttling began, for the whole shuttle session. When `shuttlePlay()`/`returnToLive()` later committed playback at the landed time, `checkBreakState` saw the stale key, concluded a break "just ended," and `endBreak` credited `viewNow() - S.breakEnteredAtMs` (a `breakEnteredAtMs` from *before* shuttling, against a `viewNow()` now off in shifted time) — a huge garbage delta into the new `S.contentLostMs`, plus a redundant `playChannelLive` call racing the one already in flight. Separately in the same session: `exitTimeMachine()`'s default (non-`toLive`) path never called `playChannelLive` at all — it only hid the VCR OSD — so exiting mid-shuttle via the `T` key left the video permanently paused on whatever frame the scrub preview last seeked to, since `updateShuttlePreview` never calls `.play()`. **Why:** this class of bug is easy to introduce and easy to miss in review — the code that *sets* a piece of state (here, break tracking) is far away from the code that *diverges from real time* (shuttle), so nothing visibly breaks until you exercise the specific combination (shift time while a break is on screen, then resume) days or sessions later.
**How to apply:** Whenever adding a new entry point that stops tracking real time (a new preview/scrub mode, a new "paused" state) or a new piece of state that assumes continuous real-time progression, audit every existing "enter preview / diverge from live" function (`startShuttle` is the canonical one today) to confirm it resets that state, and audit every "resume live" function (`shuttlePlay`, `returnToLive`, `exitTimeMachine`, `tuneToChannel`, `powerOn`) to confirm it actually calls `playChannelLive` (or equivalent) rather than just updating UI chrome.

**A break's scheduled `windowEnd` (from `entryDurationS`/`probeDuration`, a one-time-probed file duration) is an estimate, not ground truth — live playback must trust the real `<video>` element's own `ended` event over it when they disagree, without breaking the deterministic-pure-function-of-time model breaks otherwise use (see the `viewNow()` entry above).** Fixed 2026-08-06 (session 7): `checkBreakState` (`playback.js`) used to cut a bumper off the instant the boundary timer fired, even if the real file (re-encoded, misread container duration, etc.) was still genuinely playing past its probed length. **CSS gotcha confirmed 2026-08-16: `transition: <prop> …` on a property whose only specified value is `calc(var(--custom-prop) * N)` does not reliably retrigger when only the custom property changes — the property can get stuck at its very first computed value forever.** Found building the DISPLAY tab's live CRT-preview swatch (`#crt-preview`, setup.css): `border-radius: calc(var(--crt-curvature, 0) * 14px);` plus `transition: border-radius 0.15s ease;` meant dragging the CURVATURE slider updated `--crt-curvature` correctly (confirmed via `getComputedStyle(el).getPropertyValue('--crt-curvature')`) but `getComputedStyle(el).borderRadius` stayed at `0px` no matter what — even waiting well past the transition duration, even setting the custom property fresh under a brand-new name. **CSS gotcha confirmed 2026-08-16: two same-specificity rules that both target an element (a generic "hidden by default" class and that element's own specific class) tie-break on source order, not on which one is "meant" to win — so an element's own layout rule setting `display: flex` as part of its intrinsic styling will silently defeat a `display: none` toggle rule of equal specificity that comes earlier in the file, regardless of any attribute/state scoping on the toggle rule.** Found building the four new theme screensavers (`.screensaver-variant{display:none}` as the shared "hidden unless this theme is active" base, `overlays.css`): each variant's own block (`.screensaver-testcard`, `.screensaver-standby`, `.screensaver-lineup`, `.screensaver-diagnostics`) also specified `display: flex` as part of its normal box layout (flex-direction/align-items/etc.), at the exact same specificity (one class) as `.screensaver-variant`. **Why:** easy to miss in review because each individual rule reads correctly in isolation — the bug only exists in the *combination* of "a shared hide-by-default class" and "a specific class that also happens to set the same property for unrelated layout reasons," and only shows up by actually toggling the state live, not by reading the CSS.
**How to apply:** When adding a new "hidden unless active" element controlled by a shared class (`.X-variant{display:none}`) plus a specific-class layout rule for the same element, the specific-class rule must never itself set `display` — put every other layout property (`flex-direction`, `gap`, `align-items`, `background`, `position`) there, but leave `display` to be set *only* by the shared base rule and the state-scoped "on" rules. Verify any multi-state toggle group like this by actually cycling every state live (not just eyeballing the CSS) and checking that exactly one variant computes visible at a time — this is the second time in this file a bug of this shape was only caught by driving the real page via CDP rather than reading the stylesheet.

**Gotcha confirmed 2026-08-17: a new `dom.js` export used in one file but never added to that file's own `import {...} from './dom.js'` block throws a plain `ReferenceError` at module-evaluation time — not deferred to when the referencing function actually runs — which can silently break the app's entire boot with no visible error at all.** Happened for real building the PERFORMANCE tab's "BOX STATUS" panel in a 14-feature batch: `boxStatusCheckBtn` (and its sibling refs) were exported from `dom.js` and used at the top level of `setup-channels.js` (`if (boxStatusCheckBtn) { boxStatusCheckBtn.addEventListener(...) }`, unconditional module-scope code, not inside a function), but never added to that file's own import list. **Why:** this class of bug is invisible to every static check this project's CDP discipline otherwise relies on (per-file `node --check`, the static import/export graph checker), and — critically — invisible to a *naive* live boot test too, if the error listener gets attached after the page has already loaded. **Gotcha confirmed 2026-08-17: two different hostnames under this app's custom `app://` scheme (e.g. `app://bundle/...` the page itself, `app://plugins/...` a new one) are separate *origins* by ordinary web rules, so `fetch()`/dynamic `import()` from the page to the other hostname is CORS-gated even though both are served by the same `protocol.handle('app', ...)` function — and a `<link rel="stylesheet">` to that same other-origin URL loads fine regardless, because stylesheet links aren't CORS-gated. **How to apply:** Any future addition of a new hostname under the `app://` scheme (or any other custom scheme) that needs to be `fetch()`/`import()`-able *from a page served at a different hostname of that same scheme* must add both pieces, not just one. **Bug confirmed 2026-08-19: an IPC handler that does its own `loadConfig()`/`saveConfig()` round-trip straight to disk (bypassing the renderer's cached `S.config`) creates a silent revert race with the renderer's own debounced autosave, which always writes the *whole* `S.config` object wholesale.** Found diagnosing "REVIEW & APPROVE PERMISSIONS keeps showing even after approval" (`setup-plugins.js`): clicking APPROVE called `window.api.pluginsApproveCapabilities(p.id, signature)`, whose `plugins:approveCapabilities` handler (`main.js`) did a fresh `loadConfig()`, set `config.plugins.approvedCapabilities[id]`, and `saveConfig(config)` — correct on disk, but `S.config` in the renderer was never updated to match. **CSS gotcha confirmed 2026-08-21: giving a container `display: flex; flex-direction: column` (e.g. to add consistent `gap` spacing between its children — a real fix applied to the AUTO-CURATE editor/preview cards, see [[retro_cable_box_auto_curation]]) silently stretches every lone child to the container's full width, including buttons that were previously fine at their natural content width under the container's old default (block) display — `align-items` defaults to `stretch`, and that applies to *all* children uniformly, not just the ones meant to be full-width rows.** Hit three times in one pass while adding padding/section-grouping to the AUTO-CURATE cards: the day-part editor's "+ ADD SLOT" button, the "ADVANCED: DAY-PART TEMPLATE" toggle, and the "+ NEW PROFILE" button all rendered as full-card-width bars once their parent gained `flex-direction: column`, even though nothing about the buttons themselves changed. **Geometry gotcha confirmed 2026-08-21: `clientWidth`/`clientHeight`/`offsetLeft`/`offsetTop` are PRE-transform, local-coordinate-space measurements (the box a `position:absolute` CHILD of that element would size/position itself against); `getBoundingClientRect()` is the real POST-transform SCREEN box. Two elements that need to visually line up but sit on opposite sides of a transformed ancestor — one nested inside it, one a sibling outside it — silently drift apart if their geometry code mixes the two measurement types, and this only manifests when the transform is actually non-identity (easy to miss in a quick check).** Found building `applyTvCabinet` (`power.js`, see [[retro_cable_box_captions_and_tv_cabinet_plan]]): `#tv-cabinet` is a sibling of `#display-frame` (deliberately, so its art can bleed past `#display-frame`'s own `overflow:hidden`), while `#player` is a real descendant of `.crt` (itself inside `#display-frame`). `#display-frame` gets a `transform: scale(...)` whenever AUTO display mode's simulated-resolution feature is active (`--display-frame-transform`, `display-mode.js`). `#player`'s own `position:absolute` math correctly used `crtContainer.clientWidth/clientHeight` (pre-transform local space, matching how its own inline left/top actually get interpreted). `#tv-cabinet`'s sizing wrongly reused that SAME pre-transform value instead of `crtContainer.getBoundingClientRect()` (the real post-transform screen box it actually needed, being outside the transformed ancestor) — producing a cabinet scaled to 1.107x instead of the declared 1.3x, with ~150-190px of drift between the SVG's drawn screen-cutout and the actual video position. The user caught this live (a real screenshot showing a small floating video with a big colored gap around it) — an earlier CDP "verification" pass had missed it entirely, because it only checked aspect-ratio math and computed-style values, never a real cross-element geometry comparison against actual rendered pixels.
**Why:** it's an easy trap because BOTH measurement types return plausible-looking numbers, both are synchronous, and the bug is invisible unless the transform is actually active at test time (e.g. AUTO display mode at a non-'native' simulated resolution) — a check run with the transform at its default/identity value would show no discrepancy at all.
**How to apply:** When adding any new element that must visually align with something on the *other side* of a potentially-transformed ancestor (inside vs. outside it), explicitly decide which coordinate space each measurement needs and use `getBoundingClientRect()` for anything positioned outside/sibling-to the transformed ancestor, `clientWidth`/`clientHeight`/local math for anything positioned as a real child within it — never assume they're interchangeable. Verify with an actual geometry comparison (measure both elements' real rendered rects and compute the drift, as done here after the fact) rather than only checking that the code ran and produced plausible-looking values, and test with the transform actually engaged (a non-native AUTO display-mode resolution), not just at its default identity state.
