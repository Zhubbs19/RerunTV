Found via a static dom.js/index.html id cross-check plus a live CDP audit (tab/subtab click sweep with `window.onerror` capture) of the setup screen, per the project's standard CDP boot-test discipline ([[retro-cable-box-architecture-constraints]]).

**1. Single-click guide overlay broken on every virtual channel.** `app.js`'s `tvScreen` click handler calls `isVirtualChannel(S.currentNumber)` and `showVirtualGuideOverlay(...)` but never imported either — `isVirtualChannel` wasn't imported at all, and `showVirtualGuideOverlay` (`virtual.js`) wasn't even exported. Single-clicking the TV screen while tuned to any virtual channel (weather/Spotify/YouTube/landing/AUX/party/public access) threw a `ReferenceError` and silently did nothing, instead of showing the channel-info overlay. Fixed: exported `showVirtualGuideOverlay` from `virtual.js`, imported both into `app.js`. Verified live via CDP (dispatched a real click on `tvScreen`, confirmed the guide overlay appears with no error).

**2. Party floating-reaction emojis mispositioned.** `renderFloatingReaction()` (`party.js`) looked up `document.getElementById('crt-container')` — an ID that doesn't exist anywhere in the codebase — always silently falling back to `document.body`. `.floating-reaction` is `position: absolute` and needs a `position: relative` ancestor matching the actual TV picture (`.crt`, exported as `crtContainer` in `dom.js`) to land correctly; appended to `<body>` instead, its `left: %`/`bottom: px` resolve against the full window instead of the TV screen, so guest reaction emojis could land off the picture whenever the window is larger than the CRT area. Fixed: use the existing `crtContainer` export instead of the dead id lookup.

**3. SHUFFLE ORDER checkbox reshuffles on any `checked: true` change, not just a real off→on transition.** `setup-channels.js`'s shuffle-checkbox handler ran `shuffleArray(ch.files)` any time the box's `change` event fired with `checked === true`, with no check of the *previous* value — so a channel that already had shuffle on could get silently re-shuffled again by any spurious/duplicate `change` event, not just a genuine user-initiated off→on toggle. This is the same failure class that already caused real, permanent data loss once before in this project (a CDP test selector bug that hit real channel 4's SHUFFLE checkbox, permanently reshuffling ~228 files — see the CDP boot-test discipline entry in [[retro-cable-box-architecture-constraints]]). Confirmed live during this session's own audit: a blind checkbox-toggle sweep (toggle every checkbox off then back on, to test for wiring errors) re-triggered this on 13 real channels simultaneously, requiring a full config restore from backup. Fixed by capturing `wasOn = !!ch.shuffle` before the assignment and gating the reshuffle on `!wasOn`, so only a genuine off→on transition reshuffles; toggling back to an already-on state is now a no-op for the file order.

**How to apply:** any future audit of a checkbox/toggle whose `change` handler has a real, non-idempotent side effect (reordering files, spawning a process, hitting an API) should check whether that side effect is gated on an actual state *transition* or just the new value — the latter is the exact shape of bug this file documents twice now. When live-testing checkboxes via CDP for wiring bugs, prefer testing state transitions individually (single explicit toggles with the resulting state checked) over a blind toggle-all-then-toggle-back sweep — the sweep itself is what reproduced this bug's blast radius across 13 channels at once, on top of the confirmed [[retro-cable-box-cdp-visible-window-gotcha]] incident from the same session.
