Mid-session pivot from the interstitials-spec work: the user wanted a universal remote for the app, controllable from a phone. Chose the simplest, most universal form after discussion — a page served by a small local HTTP server the app itself hosts, opened in the phone's browser (no app install, works on any phone including iPhone, unlike a native Android app which was considered and rejected as *more* work here — no Android toolchain exists in this repo and it would only cover Android). Explicitly confirmed LAN-only: no internet exposure, no port forwarding, same trust model as a physical remote (no auth in v1).

**Architecture, all shipped:**
- **`main.js`**: a plain Node `http` server (no new npm dependency) bound to `0.0.0.0:8721`, started alongside `createWindow()`. Serves the new `remote/` directory's static files (reusing the existing `mimeFor` MIME map and the same path-containment check pattern as the `app://` bundle handler), `POST /command` relays `{key, shift}` straight into the renderer via `mainWindow.webContents.send('remote:command', ...)`, `GET /state` returns a small cached `{number, name}` for the phone page's "NOW WATCHING" line.
- **The key insight that made "full parity" cheap**: the entire keyboard map was already one function — `renderer/js/app.js`'s `window.addEventListener('keydown', (e) => {...})` callback, a single `switch(e.key)` covering every shortcut. Extracted (zero logic changes) into `export function handleKey(e)`, called both by the real listener and by a new `window.api.onRemoteCommand((cmd) => handleKey({key: cmd.key, shiftKey: !!cmd.shift, preventDefault(){}}))` — every existing behavior (digit-entry buffering/auto-commit, guide-grid interception, wake-on-any-key, time-machine shuttle) came along for free, no duplicated logic.
- **`remote/` directory** (project root, sibling to `renderer/`, deliberately *not* part of the ES-module bundle — plain script, no build step): `index.html`/`style.css`/`remote.js`. Buttons for every shortcut (number pad, D-pad for nav/surf/shuttle, dedicated FAV▲/▼ since phones have no Shift key, full functions grid). Uses `pointerdown` (not `click`) for button activation specifically to avoid mobile's ~300ms tap-delay, and fire-and-forget `fetch()` calls (never awaited) since the button's own `:active` CSS is the user's actual feedback, not the round-trip.
- Setup screen (AUDIO & SYSTEM tab) shows the LAN URL(s) to open on the phone, computed live (not cached in config, since it needs to track whatever network the machine is on right now).

**Real bug caught during testing, worth remembering the pattern of:** the first "which IP is the LAN address" implementation just took the first non-internal IPv4 adapter from `os.networkInterfaces()` — on the actual dev machine this returned a Tailscale VPN's **link-local** address (`169.254.x.x`, never phone-reachable) before ever reaching the real WiFi adapter (`192.168.1.70`). A real machine commonly has several simultaneous non-internal adapters (VPNs — Tailscale, NordLynx/WireGuard — plus virtual switches from VirtualBox/VMware/Hyper-V) and "first" is not a reliable heuristic. Fixed by filtering out link-local addresses always, filtering adapter names matching a VPN/virtual-adapter pattern (`/vpn|tailscale|nordlynx|wireguard|zerotier|hyper-v|virtualbox|vmware|loopback|utun|tap\d|tun\d/i`), and — since name-based filtering still can't always distinguish a same-subnet virtual adapter (e.g. a "VirtualBox Host-Only" adapter Windows just labels "Ethernet 2") from a real one — showing **every** surviving candidate to the user with its adapter name, rather than confidently guessing one that might be wrong. **How to apply**: any future feature that needs "the machine's real LAN/network address" should reuse `getLanUrls()` (main.js) rather than re-deriving this, and should keep the "show all candidates, let the user recognize their own WiFi name" pattern rather than trying to pick one automatically — on a real dev/gamer machine, VPNs and virtual adapters are the norm, not the exception.

**Verification**: live end-to-end via plain `curl` against the running app's real HTTP server (not just unit-style pure-function tests, since this feature's whole point is the actual network layer) — digit entry (channel 67→4), channel-up (4→5), guide open/close, mute toggle, all confirmed via CDP DOM checks after each command. Config diffed clean throughout (no scratch data touched real config, since testing the remote flow never required creating scratch channels).

**How to apply**: if extending remote control further (e.g. a "now playing" richer status, or per-user PINs), the pieces to touch are `main.js`'s `startRemoteServer`/route handling, `remote/remote.js` for new buttons, and `handleKey` (app.js) only if a *new* app-side action is needed — most future remote features should need zero renderer-side additions beyond a new button, since `handleKey` already covers everything reachable by keyboard.
