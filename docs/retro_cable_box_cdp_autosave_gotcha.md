**`saveConfigDebounced()` (`state.js`) fires from `playback.js`/`power.js` call sites (tuning a channel, powering on, etc.), not just from explicit "Done"/export actions — a CDP test that calls `showTvScreen()` or otherwise starts playback while scratch data is sitting in `S.config` can autosave that scratch data to the real on-disk config within its default 600ms debounce, before an in-memory cleanup filter later in the same script ever runs.**

**Why:** confirmed for real 2026-08-05 during the guide-freeze fix's stress test — 70 scratch channels (numbers 9001-9070) were pushed into `S.config.channels` in-memory to stress-test `renderGuideGrid()`'s lazy-fill chunking, then `showTvScreen()` was called to open the guide. That call path touches playback/tuning, which called `saveConfigDebounced()`, and the 600ms timer fired and wrote all 83 channels (real 13 + scratch 70) to the real `channels.json` well before the script's later in-memory `S.config.channels = S.config.channels.filter(...)` cleanup ran — so the cleanup only fixed memory, not disk. The on-disk pollution wasn't caught until an explicit post-test `diff` against the pre-test backup, by which point a separate `rm` of that backup (done reflexively right after seeing the diff, without reading the diff output first) had already destroyed the one clean copy — the diff was mistaken for a "no differences" check before it was actually inspected. Recovery required hand-filtering `number >= 9000` entries out of the polluted on-disk file and re-`JSON.stringify(config, null, 2)`-writing it (matching `main.js`'s save format) rather than a full restore, since older same-day backups had already-stale data (a channel rename that happened later in the day) that a full restore would have silently reverted.

**How to apply:**
1. Any scratch data added to `S.config` for a CDP test — extra channels, a mutated block, anything — must be treated as at risk of hitting disk the instant any playback-adjacent function runs (`showTvScreen`, `tuneToChannel`, `powerOn`, or anything that calls into `playback.js`/`power.js`), not just at the point an explicit save button is clicked. Prefer to do scratch-data mutation and cleanup within the same tight sequence, and re-check `S.config.channels.length` (or whatever was mutated) right after any such call, not just at the end of the script.
2. Before deleting *any* pre-test backup file, actually read the `diff` output (or an explicit `diff ... && echo CLEAN` style check) rather than running the deletion unconditionally after the diff command — a non-zero diff exit code means the backup is the thing you still need, not a stale artifact to clear away. Losing the pre-test backup turns a two-command restore into a manual reconstruction.
3. When the pre-test backup is gone and older backups exist, don't assume the newest older backup is safe to restore wholesale — diff it structurally against what you know changed (e.g. a specific channel's name/fields) before trusting it, since same-day backups from an earlier session can already be stale relative to the current session's edits. Hand-repairing the polluted live file (filter out the known-bad entries, re-save in the app's own `JSON.stringify(config, null, 2)` format) is safer than restoring from a backup of unknown recency.

**Second recurring gotcha, confirmed twice on 2026-08-05: clicking a real REMOVE button via CDP hangs the whole session.** Several delete-confirmation flows (`window.confirm(...)` in `setup-channels.js`, both single-channel and bulk remove, and the config-import overwrite prompt) use the browser-native `window.confirm()`. In Electron this is NOT a Chromium `Page.javascriptDialogOpening` event — CDP's `Page.handleJavaScriptDialog` returns `"No dialog is showing"` and does nothing, because Electron implements `confirm()` via a synchronous IPC call to the main process that blocks the renderer's JS thread entirely until a human clicks a real native OS dialog button. Any subsequent `Runtime.evaluate` call just hangs (times out at the tool's 120s ceiling) with no way to dismiss it programmatically. **How to apply:** never click a REMOVE/delete/import-overwrite button via CDP `.click()` in this codebase — there is no way to un-hang it short of killing the Electron process. Instead, either (a) delete the scratch channel/entry by editing the on-disk config JSON directly after cleanly closing the app (`Browser.close` still works fine when no dialog is open), or (b) if the removal must happen while the app is running, avoid triggering the confirm at all — e.g. add scratch channels with a name AND no files so they get pruned automatically by the existing `doneBtn` handler's `c.files.length > 0 || (c.name && c.name.trim())` filter (this is real, pre-existing cleanup logic in `setup-channels.js`, not something to rely on for real channels but a legitimate escape hatch for a nameless-and-fileless test scratch channel specifically).

**Third gotcha, same day: batch-removing items from a live re-rendering list via a pre-snapshotted array silently only removes every-other-one.** Cleaning up scratch interstitials-pool entries by doing `Array.from(list.children).forEach(row => clickRemoveOn(row))` only removed 1 of 2 rows — each REMOVE click calls `renderInterstitialsList()` which does `innerHTML=''` and rebuilds every row from scratch, so the *second* row reference in the pre-snapshotted array is a detached node from before the rebuild; clicking its (now-orphaned) button still fires the handler with a stale closure-captured array index, which by then points at the wrong element in the shrunk pool. Real consequence this time: a genuine pre-existing pool entry (a real Christmas commercial, not a scratch artifact) got caught in the same removal loop and deleted from the live in-memory config alongside the actual scratch entries — caught immediately by checking `S.config`-equivalent state via the on-disk file before trusting the cleanup, and recovered because the interstitials REMOVE handler does **not** call `saveConfigDebounced()` at all (unlike channel/block removal), so the accidental in-memory deletion never made it to disk before the app was closed. **How to apply**: never batch-remove from a list that re-renders on each removal using a snapshot taken before the loop starts — re-query the live list fresh before each single removal instead (`while (list has a row) { find first row; click its remove; wait for re-render }`), and after any bulk cleanup involving REMOVE-style buttons, diff the specific data structure touched (not just "did the file change") to confirm the count/content matches expectations, not just that nothing *else* broke.

**Fourth gotcha, same day: `cell.style.background = X` (the CSS shorthand) silently discards `background-image` set by a stylesheet class on the same element.** Cost real debug time chasing why a `.calendar-day-empty-block` stripe pattern (defined via `background-image: repeating-linear-gradient(...)` in a CSS class) never rendered even though the class was confirmed present in the DOM — a sibling line of code set `cell.style.background = hexToRgba(...)` for the day's color tint, and the `background` shorthand resets every sub-property it doesn't mention, including `background-image`, with inline style always beating a stylesheet rule regardless of specificity. Fix was changing the inline write to the longhand `cell.style.backgroundColor`. **How to apply:** whenever inline-styling an element's background color via JS on an element that might also carry a CSS-class-driven `background-image`/`background-position`/etc., use the specific longhand property (`backgroundColor`), never the `background` shorthand — true throughout this codebase, not just the calendar.

**Sixth gotcha, 2026-08-17: editing a bundled plugin's source under `plugins/<id>/` in the repo does NOT affect the already-running app until the plugin is re-seeded — `seedBundledPlugins()` only copies a bundled plugin into `userData/plugins/<id>/` once, the first time that folder doesn't exist, and never overwrites it again.** Confirmed twice fixing the breaking-news headline-textarea CSS bug (see [[retro_cable_box_architecture_constraints]]'s `.panel-body` shrink-wrap entry): edited `plugins/breaking-news/renderer.js` in the repo, killed and relaunched the app fully via CDP, and the bug was still there — because Electron loads plugin renderer.js from `userData/plugins/breaking-news/renderer.js` (the seeded copy from an earlier session), not the repo source, and that copy was stale. A full app restart is necessary but **not sufficient** to test a plugin source edit — the fix only took effect after manually `cp`-ing the repo's updated file over the corresponding file in `userData/plugins/<id>/`.
**Why:** this "never overwrite once seeded" behavior is deliberate (so a user's own edits/disables to an installed plugin survive across app updates), but it means the repo source and the installed copy silently diverge the moment you edit the repo after the plugin has ever been seeded once — which, in this dev environment, is almost always the case by the time you're iterating on a fix.
**How to apply:** After editing any file under `plugins/<id>/` in the repo, before CDP-testing the change, either (a) `cp` the specific changed file(s) into `userData/plugins/<id>/` (fast, what was actually done both times), or (b) delete `userData/plugins/<id>/` entirely and let the next boot's `seedBundledPlugins()` do a fresh copy (slower, but also picks up new/removed files within that plugin, which a targeted `cp` won't). Don't conclude a plugin fix "didn't work" from a CDP test until you've confirmed the installed copy actually matches the repo source (`diff repo-path userData-path`).

**Fifth gotcha, 2026-08-17: backing up the OS-profile `channels.json` (`%APPDATA%/retro-cable-box/channels.json`) before a CDP test is not enough — main.js's portable-install migration (see [[retro_cable_box_architecture_constraints]]) can silently switch the app to a *different* live config file the very first time it launches in a session.** `main.js` prefers a local `<repo>/userData/` folder over the OS-profile path, and one-time-migrates the OS-profile data into that local folder the first time it finds the local folder missing — this can trigger on literally the first CDP-test launch of a session, after which every subsequent launch reads/writes `<repo>/userData/channels.json`, not the OS-profile file. Confirmed the hard way: backed up `%APPDATA%/retro-cable-box/channels.json` before testing the ticker/screensaver/vintage-audio/smpte-test-pattern plugin migration, ran several launches, then found the OS-profile `plugins/` folder still empty afterward even though `window.RCBPlugins` showed all 4 new plugins loaded — the app had switched to `<repo>/userData/` on the very first launch and every plugin/config read-write after that point went there instead. The OS-profile backup I'd made was backing up a file the app was no longer touching at all, giving false confidence. A stray test mutation (`S.config.ticker.text` toggled during a settings-panel exercise, never explicitly saved by the test script) got picked up by the app's own periodic rotating-backup/autosave and persisted to the *real* live file at `<repo>/userData/channels.json`, silently, well after the test's own cleanup step ran. **How to apply:** before trusting any pre/post-test config diff, confirm which `userData` directory is actually live for *this specific launch* — the simplest check is `ls <repo>/userData/` (does the portable folder exist at all yet?) before assuming the OS-profile path is still authoritative; if a local `userData/` folder exists or gets created during the test, back up and diff *that* file, not the OS-profile one. The app's own `userData/backups/channels-<timestamp>.json` rotation (kept automatically, roughly every 15-20 min) is a reliable source of a clean recent snapshot to diff against even if you didn't make your own pre-test backup in the right place — compare pretty-printed+sorted JSON (`python3 -c "import json; print(json.dumps(json.load(open(f)), indent=1, sort_keys=True))"` on both sides, then `diff`) to isolate the exact field(s) that drifted rather than eyeballing an 800KB+ file.
