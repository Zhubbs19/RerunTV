Shipped a plugin system foundation (main-plugins.js, [renderer/js/plugins.js](../renderer/js/plugins.js), [renderer/js/setup-plugins.js](../renderer/js/setup-plugins.js), PLUGINS setup tab) plus a single custom-CSS-file loader, plus made `userData` portable. Extended over 2026-08-17→18 to migrate everything: [[retro_cable_box_plugin_migration_candidates]] is fully closed. As of 2026-08-18, migration is genuinely complete on BOTH sides (main-process AND renderer) — see the registerSettingsPanel section below. This matters a lot for [[retro_cable_box_foss_parity]]: core files must stay identical between retro-cable-box and retro-cable-box-foss, so any plugin-specific UI (a channel's whole display, a settings panel) has to be plugin-owned, not hardcoded into core index.html/state.js/virtual.js — otherwise the FOSS build (which omits Spotify Connect/YouTube Music/Party Jukebox) would need core to diverge too.

**How to apply:** any new "talks to an external process/API" or "runs its own LAN server" feature should be built as a plugin from the start, main-process AND renderer halves both — that's the established default now, not an aspiration.

## Plugin shape
`<userData>/plugins/<folder>/manifest.json`: `{id, name, version, description, style, renderer, main, dependsOn}` — style/renderer/main/dependsOn all optional.
- `style` (CSS) and `renderer` (ES module) served over `app://plugins/...` (cross-origin from `app://bundle/...` — needs `corsEnabled` + CORS header, see main-protocol.js). The reverse direction does NOT work: `app://bundle/...` is served WITHOUT the CORS header (main-protocol.js's fallback branch), so a plugin's renderer.js can never `import` a core renderer module directly — everything a plugin needs from core must come through `ctx` (see below).
- `main` (CommonJS) runs via `require()` in the main process, full Node/Electron access, deliberately no sandbox. Exports `activate(ctx)`.
- Renderer registration: `window.RCBPlugins.registerChannelType(id, {number, label, nowText, badge, render(container, ctx), stop(ctx)})` for a plugin-owned virtual channel — `render()` builds the channel's ENTIRE UI into `container` via `innerHTML`/DOM creation (virtual.js wipes `container.innerHTML` on every tune-away, so nothing persists across renders except what the plugin keeps as its own module-level JS state). Built-in system channels (PARTY_CH, HBO_CH, etc.) still stay hardcoded in virtual.js — only plugin-provided channels (Spotify Connect CH4, YouTube CH93, both migrated 2026-08-18) use this path. Built-ins win on a number collision.

## `registerSettingsPanel` + `window.RCBPlugins.ctx` (added 2026-08-18)
- `window.RCBPlugins.registerSettingsPanel(id, {render(container, ctx)})` — a plugin's own settings UI (toggle, path field, whatever), rendered into a dedicated container appended to `#plugin-settings-slot` (lives in the PROGRAMMING tab's ON-SCREEN EXTRAS subtab, index.html). Called fresh every time `renderSettingsPanels()` runs (setup-settings.js) — same "clear and rebuild, don't assume first-call" contract as a channel type's `render()`. `ctx` = `{S, saveConfigDebounced, selectExecutable}`.
- `window.RCBPlugins.ctx` = `{S, viewNow, player}` — the SAME shape passed to a channel type's `render()`, but available **synchronously at a plugin's own top-level code**, before that plugin's channel has ever been rendered even once. Needed because a plugin's IPC listeners (e.g. spotify-connect's `onSpotifyStatus`) can fire before the user ever tunes to its channel, and still need to write into `S` for whenever they do. Set in `installGlobalApi()` (plugins.js) before any plugin `renderer.js` is dynamic-imported.
- A plugin seeds its own `S.config.<key>` defaults at its own top level too (`if (!S.config.spotify) S.config.spotify = {...}`) — core `app.js`'s `applyConfigDefaults` no longer seeds plugin-specific config at all.
- **Renderer-side plugin loading does NOT respect `dependsOn` order** (only the main-process `loadMainPlugins()` does, via `orderByDependencies`) — `window.api.pluginsList()` returns plugins in whatever order `discoverPlugins()` found them, and `plugins.js`'s `loadPlugins()` imports each renderer.js in that same order. Any renderer-to-renderer dependency (e.g. party-jukebox needing youtube-music's queue functions) MUST be resolved lazily at event-fire time, never at a plugin's own top level, or it's a load-order race.
- **Cross-plugin renderer API**: when core (power.js) or another plugin (party-jukebox) needs to call into a plugin that might not be installed, that plugin exposes a small object directly on `window.RCBPlugins.<camelCaseId>` (e.g. `window.RCBPlugins.youtubeMusic = {enqueueItem, skipTrack, resumeYoutubeOverlayIfNeeded, overlayAudioEl}`) — always null-checked by the caller. This is deliberately ad hoc (not a formalized service registry like the main-process `ctx.services`) since only two callers exist so far; formalize it if a third shows up.
- **A persistent DOM element (e.g. an `<audio>` for background/overlay playback) must NOT live inside a channel-type's `container`** — virtual.js does `container.innerHTML = ''` on every tune-away, which would destroy it mid-playback. Create it once at the plugin's own top level and `document.body.appendChild()` it instead (see youtube-music/renderer.js's `overlayAudioEl`).

## Settings-panel migration wave 2 (2026-08-18): TMDB/NOAA/Party Channel/Universal Remote
All four now use `registerSettingsPanel` too — `index.html`/`dom.js`/`setup-settings.js` no longer hardcode any plugin's settings UI at all. Two new patterns that came out of this:
- **`window.<coreFn>` exposure for core functions a settings panel needs to call**: `alertDialog`, `applyTickerState`, `startTriviaRound`, `scheduleNextNoaaPoll` are now set on `window` in app.js (same spot as the existing `window.checkBreakState`/`window.tuneToChannel`). A plugin's settings panel calls these the same way it'd call any other cross-origin-blocked core function — always via `window.X`, never an import.
- **A plugin's config can live inside a config namespace CORE still owns**, when core code genuinely depends on that shape existing independent of the plugin. NOAA's `noaaEnabled`/`lat`/`lon` live inside `config.eas` (shared with the core random-EAS-test feature) — the default-seeding for `config.eas` stays in app.js's `applyConfigDefaults` (core reads it too), while only the NOAA-specific *settings fields within it* moved to the plugin's panel. Contrast with Spotify/YouTube/TMDB, which own their whole top-level `config.<key>` namespace and seed it themselves. Rule of thumb: if only the plugin reads a config value, the plugin seeds it; if core also reads it, core keeps seeding it.
- **EAS as a whole was deliberately NOT made a plugin** in this pass — only the NOAA-specific slice of it (the real-alerts settings) moved out. The random-test-slate mechanism (scheduleNextEas/runEasTest/the interrupt overlay) stays core because it's genuine box behavior with no external dependency, and because fully extracting it would need a new "interrupt overlay" plugin pattern (no channel number, not a settings-only concern) that wasn't built yet — flagged as a possible future pass, not started.

## Split-out example: party-jukebox (2026-08-18)
The YouTube guest jukebox used to be built into party-channel directly. Split into its own `party-jukebox` plugin (`dependsOn: ["party-channel", "youtube-music"]`, both soft) specifically because it's a YouTube integration, which has no business being bundled into the base party-page plugin. Two halves:
- **main.js**: registers routes via `ctx.registerPartyRoute(method, pathname, handler)`, checked by party-channel's own server via `ctx.dispatchPartyRoute(...)` on every request that doesn't match one of its own built-in routes. (2026-08-19: this replaced an earlier `ctx.services.partyRoutes` plain-array mechanism — see [[retro_cable_box_plugin_sandboxing_phase2]] for why: both plugins are now isolated processes, so a route `handler` can't be handed a live `req`/`res` across the boundary and became a pure function of a plain request/response descriptor instead, relayed by the host.)
- **renderer.js**: listens for `party:jukeboxAdd`/`party:jukeboxSkipVote`/`party:jukeboxFun` (sent by its own main.js) and drives `window.RCBPlugins.youtubeMusic`. The party guest page itself (`plugins/party-channel/party/party.js`) feature-detects the JUKEBOX tab via a real `GET /jukebox` request (405 if the plugin's routes were never registered) rather than assuming it's always present — hides the tab button entirely if absent.

## `dependsOn` + shared `ctx.services` (added 2026-08-17/18)
- `manifest.json`'s `"dependsOn": ["other-plugin-id"]` controls **load order only** (Kahn's-algorithm-style topological sort in main-plugins.js's `orderByDependencies`) — it is NOT a hard requirement. A plugin whose dependency is missing/disabled still activates (just last in line), so `dependsOn` is safe to use for both hard requirements (ffmpeg-transcode) and soft/optional ones (party-channel ↔ universal-remote's shared reaction-emoji list, party-channel → youtube-music's jukebox search).
- `ctx.services` is **one shared plain object**, the same reference passed to every plugin's `activate(ctx)` — a plugin publishes a capability by mutating it (`ctx.services.ffmpegPath = ...`, `ctx.services.partyReactionEmoji = ...`) and a later-activated dependent (or core, after `loadMainPlugins()` returns) reads it back. Always null-check — the publisher may be disabled/missing. (2026-08-19: for an *isolated* plugin this is a snapshot taken when its process forks, not a live reference — see [[retro_cable_box_plugin_sandboxing_phase2]]. A function-valued capability like `youtubeSearch` can't cross a process boundary as a plain value at all anymore — that now goes through `ctx.registerService`/`ctx.callService` instead.)
- `ctx` also carries `fetchJsonCached`, `getMainWindow`, `getLanAddresses`, `readJsonBody`, `trackConnection`, `mimeFor`, `loadConfig`, `busboy`, `QRCode`, `getPartyUrls`, `getViewerUrls`, `remotePort`, `partyPort`, `ffmpegStaticPath` — utilities/npm-package-references a plugin under `userData/plugins/` can't reach itself (outside the app's own `node_modules` resolution path, and can't `require()` a core `main-*.js` file by fragile relative path). **Adding a new plugin that needs an existing core utility or npm package almost always means adding one more property to this ctx object in main.js**, not inventing a new mechanism.
- **ffmpeg specifically**: main-media.js resolves the raw path (`FFMPEG_STATIC_PATH`, always computed) but only *exposes* it for spawning via `getFfmpegPath()`/`setFfmpegPath()` — main.js sets it from `pluginServices.ffmpegPath` after `loadMainPlugins()` runs, and that only gets populated if the `ffmpeg-transcode` plugin is installed+enabled. This is what makes disabling ffmpeg-transcode a real toggle (core transcode, party thumbnails, Spotify, YouTube all check `getFfmpegPath()`/`ctx.services.ffmpegPath` for null and degrade with a friendly message) rather than a fake one.

## IPC fallback pattern (core, main.js's `registerApiFallbackHandlers`)
- Every plugin registers its OWN `ipcMain.handle`/`ipcMain.on` for its channels, inside its own `activate()` — main.js no longer hardcodes any of TMDB/NOAA/Spotify/YouTube/Party/Remote's handlers.
- For `ipcMain.handle` channels (renderer awaits a return value via `invoke`), main.js registers a fallback stub — but ONLY if no active plugin already claimed that channel (checked via `discoverPlugins()` + `config.plugins.disabled` BEFORE `loadMainPlugins()` runs, so there's never a double-registration crash). Fallback return shape always matches what `browser-api-shim.js` (LAN viewer) already returns for these — same "just isn't available here" contract, reused rather than invented fresh.
- For `ipcMain.on` channels (fire-and-forget, e.g. `remote:state`, `party:queueState`), **no fallback is needed at all** — `ipcRenderer.send()` to a channel with zero listeners is a silent no-op in Electron, not an error. Only `.handle`-based channels need the stub.

## Disable-warning dialog (renderer/js/setup-plugins.js)
Unchecking a plugin's PLUGINS-tab checkbox now checks the full plugin list for any enabled plugin whose manifest `dependsOn` includes the one being disabled, and shows a themed confirm dialog naming them before proceeding (cancel reverts the checkbox, no config change). Wording is deliberately "may stop working correctly" rather than "won't work" — `dependsOn` covers both hard (ffmpeg-transcode) and soft (party-channel/universal-remote, youtube-music→party-channel) dependencies and there's no manifest field distinguishing the two, so the wording has to stay true for both.

## Enable/disable + userData portability gotchas found via CDP testing
- Enabling/disabling a plugin (config.plugins.disabled) and newly-dropped plugin folders only take effect on restart — deliberately not hot-reloaded.
- The userData migration copy is an ALLOWLIST of this app's own files/folders (channels.json, backups/, plugins/, party-uploads/, spotify-cache/, window-state.json, api-cache.json), never a blind recursive copy.
- Migration only copies once (skipped if `./userData/` already exists).
- **Bundled plugins seed once, never re-copy**: `seedBundledPlugins()` in main-plugins.js copies each folder from the app's own `plugins/` dir into `userData/plugins/` only if that destination folder doesn't already exist — so a user's disable/edit/delete of a bundled plugin's installed copy is never stomped by a later app update re-seeding it.
- **Static assets that used to be app-root folders (`party/`, `remote/`, `vendor/librespot/`) now live inside their plugin's own folder** (`plugins/party-channel/party/`, `plugins/universal-remote/remote/`, `plugins/spotify-connect/librespot/`) — a plugin's `__dirname` is wherever it actually runs from (userData/plugins/... after seeding), so any static-asset path must be relative to the plugin's own folder, not the old app-root location.

## Bundled-plugin auto-cleanup on removal (2026-08-19)
`seedBundledPlugins()` (main-plugins.js) now tracks which `userData/plugins/<id>` folders it seeded, in a plain `userData/plugins/.bundled-manifest.json` (not config — pure loader bookkeeping, doesn't need channels.json's save timing). On each boot, any previously-seeded id whose bundled source (`<repo>/plugins/<id>/`) no longer exists gets its installed copy auto-deleted. Fixes the gap where a FOSS build dropping a plugin from its own `plugins/` folder left the stale copy sitting in `userData/plugins/` forever (seeding was always one-way/one-time, never reconciled against removals) — the PLUGINS tab list wouldn't reflect a repo-level plugin removal even after RESCAN or a full restart, since RESCAN only re-reads `userData/plugins/`, not the repo's own `plugins/`. Verified via a real two-boot CDP test: a plugin removed from `plugins/` between boots is gone from `userData/plugins/` and the PLUGINS tab by the very next boot, while a hand-installed third-party plugin (never in the seeded-manifest, regardless of id) survives untouched. Only catches removals going forward from whatever the manifest already knew about — doesn't retroactively identify pre-existing stale folders with no tracked history (a one-time manual `userData/plugins/` cleanup is still needed for those, same as always).
