**The bug:** `loadPlugins()` (`renderer/js/plugins.js`) loaded every installed plugin's `style`/`renderer` unconditionally — it never checked `S.config.plugins.disabled` at all. `main-plugins.js`'s `loadMainPlugins()` (main-process `main.js` code) *did* correctly filter by the disabled list, so a disabled plugin's `main.js` wouldn't run, but its `renderer.js` still loaded and called `registerChannelType`/`registerSettingsPanel` exactly as if enabled — which is why the user reported "disabling doesn't work, especially for virtual channels" (channels are registered from `renderer.js`, the one place that ignored the setting). Fixed by adding a `disabledIds`/`isDisabled()` check before both the `<link>` injection and the dynamic `import()` in `loadPlugins()`.

**Real-world consequence discovered while testing the fix:** the user's actual saved config already had 12 plugins marked disabled — `area-51`, `breaking-news`, `eas-alerts`, `hbo`, `screensaver`, `pay-per-view`, `retro-game-hotline`, `shopping-network`, `smpte-test-pattern`, `spotify-connect`, `synthwave-radio`, `teletext-arcade` — presumably from earlier attempts to disable them that silently no-opped because of this exact bug. Once fixed, those 12 would actually go inactive on the very next restart. Asked the user directly (AskUserQuestion) rather than guessing whether to auto-re-enable them; **answer: leave them disabled** — the saved list is authoritative now that it actually works.
**How to apply:** if this comes up again (a user asks why their disabled-plugin list looks different than expected after this fix shipped), point back to this — it's expected, not new corruption. Don't assume a long-disabled-list is stale/accidental without asking.

**Second, related request handled in the same batch: the per-checkbox "Enabling/Disabling X takes effect..." dialog was replaced with a staged-changes + SAVE CHANGES button flow** (`setup-plugins.js`). Checkbox `change` now just toggles a per-render `Map` (`pendingChanges`) and a `.pending-change` CSS border — no IPC call, no dialog. A `SAVE CHANGES (N)` button (hidden when nothing's pending) commits everything in one pass: the dependency-conflict confirm (previously per-toggle) now fires **once per Save**, listing every plugin actually affected across the whole batch, only when there's a real conflict — canceling it leaves all pending changes staged (not discarded). After a successful save, an inline status message ("SAVED N CHANGES — RESTART TO APPLY") replaces the old modal alert, set *after* the list re-renders (setting it before gets silently wiped, since re-render doesn't touch that element but was originally sequenced wrong on the first pass — caught by testing before shipping, not a live bug).

**Third, small follow-up: hint-bar items tied to an optional plugin now auto-hide when that plugin isn't active**, independent of the user's own per-item checkbox (see [[retro_cable_box_hintbar_per_item_toggle]]). `alert-test` (E) needs `eas-alerts`, `news-alert` (B) needs `breaking-news` — `applyHintBarState()` (`power.js`) checks `window.RCBPlugins.easAlerts`/`.breakingNews` presence (same guard the actual E/B key handlers already use in `app.js`) and force-hides regardless of `hintBarHidden`. Since `loadPlugins()` isn't awaited in `app.js`'s `init()`, added `loadPlugins().then(() => applyHintBarState())` so the hint bar re-syncs once plugin loading actually finishes rather than possibly rendering its provisional pre-load state. The settings checklist (`setup-settings.js`) also gets a `*` marker + tooltip on these two items now, explaining why toggling them might not visibly do anything if the backing plugin is off.

Verified via CDP with real restarts (not just live DOM checks) — disabling Text Ticker + restarting confirmed `window.applyTickerState`/the ticker-bar element/its stylesheet link all genuinely gone; re-enabling + restarting confirmed full recovery. Dependency-conflict Save-time dialog confirmed correct (only lists still-enabled dependents, e.g. disabling `ffmpeg-transcode` only flagged `youtube-music` since `spotify-connect` was already in the disabled list). Config diffed clean against a pre-test backup after the full round-trip. Synced to FOSS (diff-confirmed identical).

**Follow-up bug, same day: Party Channel (CH 5) kept showing up even with the party-channel plugin disabled — a genuinely different bug from the one above, not fixed by the `loadPlugins()` change.** Root cause: PARTY_CH isn't a `registerChannelType` plugin channel at all — it's core-rendered (`renderer/js/party.js`), a deliberate architectural choice (see that plugin's own `renderer.js` header comment: "the actual party experience... stays in core... that's genuine box behavior, not this plugin's own concern, which is just the LAN server + this settings surface"). `virtual.js`'s `virtualChannelNumbers()` only ever checked `S.config.party.enabled` (the channel's own "PARTY CHANNEL (CH 5)" toggle, which lives *inside* the plugin's settings panel) — with zero awareness of `S.config.plugins.disabled`. So disabling the plugin stopped its LAN server and made its settings panel unreachable (no way to even flip `party.enabled` back off), while the channel itself stayed fully tunable on the box, now pointing at a dead server. Fixed with a new `partyChannelActive()` helper (`virtual.js`, exported) that ANDs both conditions — reused in `app.js` for the LAN-viewer cross-link's two identical `S.config.party.enabled`-only checks, same root cause. This is a **general pattern worth remembering**: any plugin migration where "core keeps owning some of the actual rendering, plugin only owns settings/server" needs every core call site that reads that feature's own `enabled`-type config flag to also check `S.config.plugins.disabled` for the owning plugin — a plain `S.config.<feature>.enabled` check alone silently ignores the plugin layer entirely, and grep for the config-key name across the renderer is the way to find every such site (found 3 call sites this way: `virtual.js` line ~62, `app.js` lines ~811 and ~827).
**How to apply:** When "disabling a plugin doesn't actually turn X off" comes up again for a different feature, check first whether X is core-rendered-with-plugin-owned-settings (like party) rather than a full `registerChannelType` migration (like HBO/PPV/etc.) — those need this two-gate pattern; genuine `registerChannelType` plugins only needed the `loadPlugins()` fix above, since `pluginChannelTypeIds()` naturally goes empty once the plugin's `renderer.js` never loads.
Verified against the user's real config (`party.enabled: true`, `party-channel` genuinely in `plugins.disabled` — this exact combination was already sitting in their real saved config, not a synthetic test case): `virtualChannelNumbers()` excluded 5, `isVirtualChannel(5)` false, tuning to 5 fell through to the plain no-signal card (smpte-test-pattern also happened to be disabled in their real config) instead of the party channel. One test-tuning side effect (`lastChannel` mutated to 5) was caught and repaired by restoring the full pre-test backup file rather than a partial Python rewrite — Python's `json.dump` defaults to LF line endings while this app's own saves are CRLF, so a partial-content-correct rewrite still showed as 100% diff-different; always diff after any manual on-disk repair, not just trust that the intended field was fixed correctly. Synced to FOSS (diff-confirmed identical).
