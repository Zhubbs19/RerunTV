**What it is:** CH4 is a real Spotify Connect device (via librespot) you can cast to from the Spotify app's device picker, plus an on-screen now-playing card. The user's original ask went further — a matching MTV-style channel that cuts to a local music video when one's tagged for the currently-playing track, falling back to regular content otherwise — but that's phases 4-5, not yet built (see below).

**Why librespot, not the Spotify Web Playback SDK:** the user already runs librespot for a Discord bot (`C:\Users\zhubb\DiscordBots\librespot`), so it reuses known-working tooling. The SDK route would've needed Widevine DRM setup in Electron *and* a second, parallel audio pipeline outside this app's single-`<video>`-element design (see [[retro-cable-box-architecture-constraints]]'s "one player for everything" rule) — librespot sidesteps both: no DRM (it decodes the stream itself), and its raw PCM output gets bridged into the *same* `player` element everything else uses, so volume/mute/power-off all keep working on it for free. This was an explicit, discussed architecture fork — see [[retro-cable-box-architecture-constraints]]'s "no longer strictly offline" entry for the broader implication (this is the one deliberate exception to the app's offline-first rule).

**Where the binary lives:** `vendor/librespot/librespot.exe` — a copy of *just the compiled binary* (12MB) from the user's Discord-bot librespot checkout, not the ~950MB Rust source/build-cache repo. Own dedicated copy so it doesn't share process/cache state with the Discord bot. MIT-licensed, `vendor/librespot/README.md` has full provenance. Settable to a different path via Settings → AUDIO & SYSTEM (falls back to this bundled one).

**Audio pipeline (all in main.js's "Spotify Connect" section):** librespot spawned with `--backend pipe` (writes raw S16LE 44.1kHz stereo PCM to stdout, confirmed against librespot's own source — `SAMPLE_RATE` const and `pipe.rs`'s stdout-when-no-`--device` behavior) → piped into the bundled ffmpeg (`-f s16le -ar 44100 -ac 2 -i pipe:0 -f mp3 -b:a 192k`) → ffmpeg's stdout is broadcast to whichever HTTP response(s) are attached to a tiny localhost-only server on port 8723 (`GET /stream`). No buffering — a live stream, join-whenever-hear-what's-playing-now, same as tuning into a real broadcast. The renderer's `player.src` points at `http://127.0.0.1:8723/stream` only while CH4 is tuned to (see `playSpotifyStream`, virtual.js) — librespot itself runs continuously in the background once the setting's enabled (so the Connect device stays castable regardless of which channel is on screen), independent of channel tune state.

**Now-playing metadata:** librespot's `--onevent` extension point runs `vendor/librespot/onevent.ps1` on every playback event (track changed, play/pause, etc.), with event data as env vars — exact var names (`NAME`, `ARTISTS`, `ALBUM`, `COVERS`, `DURATION_MS`, `POSITION_MS`, multi-value fields `\n`-joined) were cross-checked against the user's actual librespot checkout (`src/player_event_handler.rs` + `contrib/event_handler_example.py`), not assumed from memory. The script POSTs JSON to a second localhost-only server on port 8722 (`POST /event`), which relays it to the renderer via `webContents.send('spotify:event', ...)`. Renderer-side state lives in `S.spotifyStatus`/`S.spotifyNowPlaying` (spotify.js) — CH4's UI (virtual.js) re-renders live off IPC events while tuned there.

Both ports (8722 metadata bridge, 8723 audio stream) are bound to `127.0.0.1` only — never the LAN-facing `0.0.0.0` the phone-remote server (port 8721) uses, since these exist purely for this app's own child processes to talk back to itself.

**`--onevent` gotcha (confirmed against librespot's source, not assumed):** the PROGRAM string is split on plain whitespace (`onevent.split_whitespace()`, `player_event_handler.rs`) — no shell, no quoting. `powershell.exe -NoProfile -ExecutionPolicy Bypass -File <path>` works because `powershell.exe` resolves via Windows' always-searched System32 (regardless of PATH) and this project's own path has no spaces — a `node.exe` path under a typical `C:\Program Files\nodejs\` install would have broken this exact mechanism, which is why PowerShell was chosen over a Node bridge script.

**Reserved channel number:** `SPOTIFY_CH = 4` (state.js) — this required a real fix, not just picking a free-looking number; see [[retro-cable-box-architecture-constraints]]'s dedicated entry on this (nextChannelNumber floor bug + the migration that safely renumbered this user's real channel 4 "Boomerang" to 73 on next load).

**Tested without a live Spotify session:** verified end-to-end using the *real* `onevent.ps1` script (not a mock) fed fake env vars matching a real track-changed event, confirming the full chain (script → bridge server → IPC → `S.spotifyNowPlaying` → CH4 UI) genuinely works. Also confirmed live: librespot + ffmpeg actually spawn and stay running, both HTTP servers respond, `player.src` gets set correctly on tune-in, disabling the setting cleanly kills both child processes (confirmed via `tasklist`, not just IPC status). What's *not* verified (no Premium/live session available): actual audio ever flowing through the pipe, and the device really appearing in a phone's Connect picker.

**Still open (phases 4-5, not built yet):** per-file ARTIST/TRACK tagging (the user chose manual tagging over automatic fuzzy filename matching) and the MTV-mode matching logic that cuts a channel to a tagged music video when the live Spotify track matches, falling back to regular channel content otherwise. See [[retro-cable-box-overview]] for the running build-state log.

**How to apply:** if resuming phases 4-5, the natural extension point is `S.spotifyNowPlaying` (already has `name`/`artists` to match against) plus the file-tagging pattern already built for the DETAILS page (`file.tags`, `setup-panels.js`'s TITLES tab) — likely a dedicated `file.spotifyArtist`/`file.spotifyTrack` pair (or reuse `tags`) rather than inventing a new system from scratch.

**Post-ship debugging (2026-08-06, same day): "device not showing up on phone" — root cause confirmed via actual mDNS packet capture, not guesswork.** The user's machine has ~10 network interfaces including Tailscale and NordVPN/NordLynx (both were "not on"/dormant at the service level but their virtual adapters remained enumerated). librespot's mDNS broadcast (via the `libmdns` crate, confirmed by reading its actual cached source at `~/.cargo/registry/.../libmdns-0.10.1/src/lib.rs` and `address_family.rs`) joins/sends multicast via `Ipv4Addr::UNSPECIFIED` — it does **not** respect route-table metrics or interface metrics for choosing the send interface the way normal unicast routing does; two rounds of textbook-correct Windows routing fixes (`Set-NetRoute` destination metric, then `Set-NetIPInterface` interface metric) both verifiably took effect in the routing table but had **zero** effect on which adapter the actual packet went out on. What actually worked: stopping the Tailscale and nordvpn-service Windows services outright (not just `Disable-NetAdapter` — VPN client services actively re-enable/restore their own adapter, so disabling the NIC alone doesn't stick while the service is running). Confirmed empirically at each step via a real UDP multicast listener (join `224.0.0.251:5353`, inspect `rinfo.address` on received packets) — this is the reliable way to test any future networking-adjacent claim on this machine, since routing-table state doesn't predict actual multicast behavior here.
**Why worth remembering:** two "should obviously work" fixes based on correct, verified routing-table theory both failed in practice — this is a case where empirical packet capture was the only reliable signal, and reasoning from routing docs alone would have looked done after step one while actually accomplishing nothing.
**How to apply:** if discovery breaks again after a reboot/adapter change, check `Get-Service Tailscale, nordvpn-service` first (VPN clients often auto-start), and verify with a real packet capture rather than trusting `Get-NetRoute`/`Get-NetIPInterface` state alone.

**Separate, more serious finding from the same debugging session: repeated rapid librespot connect/disconnect cycles (spawning short-lived test instances to diagnose the above) tripped Spotify's own server-side rate limiting on audio-key requests.** Confirmed directly in librespot's own verbose log: `ERROR librespot_core::audio_key] error audio key 0 2` / `Service unavailable { audio key error }` on nearly every track, plus one explicit `ResourceExhausted ... "rate limited for at least another 0 seconds"`. Symptom looked confusing from the outside — both the Retro Cable Box UI *and the official Spotify app* showed the track/UI advancing while the same audio kept playing — because Spotify's server-side Connect-state (which drives both UIs) kept advancing the queue while the *audio* never successfully loaded past the first track or two, silently skip-failing through the rest. Temporary and server-side; not a code bug, not fixable locally, just needs the rate limit to clear on its own.
**Why worth remembering:** debugging *this* feature specifically risks triggering *this exact failure mode* — any future session's diagnostic testing should avoid spawning many short-lived librespot instances against the user's real Spotify account in quick succession. If it's really needed, warn the user first and expect a possible cooldown period afterward before real playback works again.
**How to apply:** prefer a single long-running diagnostic instance over repeated spawn/kill cycles when testing this feature again. If "things stopped working after debugging" comes up again, check the librespot log for `audio_key`/`rate limited` errors before assuming a code regression — also worth checking `--verbose` output volume before leaving it running unattended: a ~90s capture produced a 230MB/42M-line log (frame-level TRACE spam), so use `--quiet` (only warn/error) for any future live capture, redirected to a file, and kill it manually rather than waiting out a long window. When redirecting a `--backend pipe` instance's output for log capture, **only redirect stderr, never stdout** — stdout is the raw live PCM audio stream and will produce an enormous binary-garbage file almost instantly if merged into the same redirect (`2>file.log`, not `>file.log 2>&1`; send stdout to `/dev/null` or leave it as the real audio pipe). Also: killing a librespot instance abruptly (bare `kill`, not graceful shutdown) can leave its `--cache`/`--system-cache` directory in a state that makes the *next* instance using that same directory exit silently and immediately with zero log output — use a fresh cache directory per diagnostic run rather than reusing one after a hard kill.
**Confirmed worse than initially estimated (still broken after a full 1-hour wait, tested with exactly one clean connection attempt, no repeated hammering):** the log now shows an explicit `ERROR librespot_connect::spirc] state update: Resource has been exhausted { Response status code: 429 Too Many Requests }` from Spotify's own Connect-state API — a real, unambiguous HTTP 429, not just the vaguer "service unavailable" seen earlier. This is a stronger signal than a simple short-window API rate limit; it looks more like an abuse/fraud-detection flag from the earlier burst of rapid device reconnects, which typically takes substantially longer to clear (hours, possibly closer to a day — genuinely unknown, Spotify doesn't document this for unofficial/librespot clients). **Do not test this feature again by spawning more connections until the user confirms a long cooldown has passed (think hours, not minutes) — every additional connection attempt while this is active risks extending or resetting whatever penalty is in effect.** If asked to check again, prefer asking the user to make exactly one attempt via the real app (or their own Discord bot) rather than spinning up another diagnostic instance myself.
