The user wants an auto-curation system that generates/refreshes whole virtual channels (programming lineup, ad-preset tagging, bumpers/interstitials) from a themed profile, eventually via three trigger modes: one-shot, manual re-run, and scheduled/background. Scoped into phases; **Phase 1 shipped 2026-08-20**: Tag System 2.0 + curation engine + one-shot wizard. Phase 2 (manual re-curate + diff UI) and Phase 3 (scheduled/background) are not started.

**What shipped (Phase 1), core (not plugin), synced to both repos:**
- Structured per-file **facets** (`file.facets = {genre[], era, mood[], contentType, dayPart[]}`) alongside the existing flat `tags[]` — facets mirror additively into `tags` (`mirrorFacetsIntoTags`, `channels.js`) so every existing tag-driven consumer (ad-preset `contentTags` matching, interstitial pool affinity) works unchanged. UI: a collapsible "+ FACETS" row per file in TITLES (`setup-panels.js`), same pattern as the existing "+ DESCRIPTION" toggle.
- `freshCurationProfile()` (`channels.js`) + `S.config.curationProfiles[]` (defaulted in `applyConfigDefaults`, `app.js`).
- New engine `renderer/js/curation.js` — pure functions (`scoreCandidate`, `buildProgrammingPlan`, `buildInterstitialPlan`, `curateChannel`, `applyCurationProposal`), deterministic per (profile, seed) via the same seeded-shuffle pattern as `interstitials.js`. Key finding baked into the design: **channel-level ad config doesn't exist anymore** — ad cadence is purely a function of a preset's `contentTags` matching a file's own tags (`resolveActiveCommercials`, `schedule.js`), so "ad density" in a profile just means tagging curated content/bumpers, not writing a commercials object.
- New UI module `renderer/js/setup-autocurate.js`, wired into a new **AUTO-CURATE** sub-tab under PROGRAMMING (5th sub-tab alongside SHOW & AD FLOWS / BUMPER & AD POOL / CADENCE & PRESETS / ON-SCREEN EXTRAS). Wizard flow: save a profile (theme seeds, target channel or new, folder scope, ad preset, bumper style tags) → PREVIEW (read-only diff card, reshuffleable) → APPLY (a normal `S.config` mutation, so it's automatically covered by the existing undo stack — no new undo plumbing needed).

**Verified via CDP boot test on both repos** (real production data in the main repo, 12 real channels): empty state, new-profile editor (real channel dropdown, real folder checklist), preview with correct fallback-to-full-pool behavior when no content matches yet, TITLES tab facets toggle — all render/function correctly, zero console errors. Config diff after testing showed only the expected one-time idempotent migration (`curationProfiles: []` + empty `facets{}` per file) — same category as every other prior schema migration in this app.

**Phase 2 shipped same day (2026-08-20):** the user picked "add-only merge" (re-curate never removes existing content) and "AUTO-CURATE tab only" (no separate re-curate button on the channel row — EDIT/PREVIEW on the saved profile IS the re-curate flow) via AskUserQuestion, which simplified scope a lot. What actually changed:
- `buildProgrammingPlan(profile, seed, excludePaths)` now takes an optional exclude set — `curateChannel` computes it from the target channel's own current file paths (re-curate only) so the theme-matching pool/60-file cap is spent on genuinely new candidates instead of re-picking files already in the channel and having them silently no-op on apply.
- `curateChannel`'s `diffSummary` gained `currentFileCount`/`targetMissing` — the preview card now reads "RE-CURATE — CHANNEL N (X FILE(S) CURRENTLY)" / "+Y new file(s) this run would add" for an existing-channel target, vs the original "PREVIEW — NEW CHANNEL" wording for a fresh one. A profile whose target channel was deleted shows a red "(REMOVED)" tag on its list row and a full warning (no Reshuffle/Apply) in preview, instead of silently doing nothing on Apply as it did in Phase 1.
- Verified via CDP against the real library: targeting CH6 (139 real files) correctly shrank the theme-matching candidate pool from 1921→1782 scanned (excluding CH6's own files), and the diff/reshuffle/target-removed paths all rendered with zero console errors. Synced to `retro-cable-box-foss` the same way as Phase 1.

**Phase 3 shipped same day (2026-08-20):** the user picked "auto-apply silently" (no queue-for-review step) and "simple preset dropdown" (daily/weekly/monthly, not free-form hours) via AskUserQuestion. What actually shipped:
- New renderer-only module `renderer/js/curation-scheduler.js` — no main-process timer needed after all (curation.js's engine is already renderer-side/DOM-free, and setup.js's module chain loads unconditionally at boot regardless of whether the setup screen is ever shown, so a self-starting `setInterval`/`setTimeout` at that module's top level was sufficient). Checks every 30 min (`CHECK_INTERVAL_MS`), first check 20s after boot; a profile is "due" when `now - lastRunAt >= SCHEDULE_INTERVAL_MS[scheduleInterval]` (daily/weekly/monthly). Guarded with `if (!window.__isViewer)` so a LAN viewer window never self-triggers it.
- `freshCurationProfile()` (channels.js) gained `scheduleInterval: 'weekly'` default; `regenerationMode` simplified from the reserved 3-value `'once'|'manual'|'scheduled'` down to just `'manual'|'scheduled'` (the `'once'`/`'manual'` distinction was never meaningfully different in Phase 1/2, so it was collapsed rather than kept as dead surface area).
- **Real bug caught during design, fixed before it shipped:** a `'scheduled'` profile with `targetChannel: null` ("create new channel") would spawn a brand-new empty channel every single interval forever, since there's no "already created" state to check against for a recurring create. Fixed by making SCHEDULED only selectable once a real target channel is chosen (the `<option>` itself is `disabled` until then) — and switching the target back to "CREATE NEW CHANNEL" silently reverts `regenerationMode` to `'manual'` rather than leaving a schedule pointed at nothing.
- A scheduled run reuses the exact same add-only `curateChannel`/`applyCurationProposal` pair as manual re-curate (Phase 2) — it just skips the PREVIEW step and calls `applyCurationProposal` directly for anything due, then shows a toast (reused the existing generic `#fun-toast` element/pattern, previously only used by the party-jukebox plugin) reading "AUTO-CURATED: <profile names>". A due profile with nothing new to add just advances `lastRunAt` without writing/toasting, so it doesn't get re-checked every 30-min tick until its next real interval boundary.
- Verified live end-to-end via CDP: dynamically `import()`-ed the already-loaded scheduler module in-page, pushed a synthetic `regenerationMode:'scheduled'` profile targeting real CH6 with `lastRunAt: null`, called `runScheduledCuration()` directly — correctly added 60 new files (respecting the existing MAX_CURATED_FILES cap), set `lastRunAt`, and showed the toast. Confirmed **no disk write actually landed** afterward (`saveConfigDebounced()`'s debounce window hadn't elapsed before the test process was killed) — the on-disk config came back byte-identical to the pre-test backup, so this was safe to run against the real 12-channel library without a restore step. Synced to `retro-cable-box-foss` and boot-verified there too (editor renders, REGENERATION select present, zero page errors).

**Why:** Big multi-part feature explicitly phased down after AskUserQuestion with the user (scope = programming+ads+bumpers+whole-channel-generation; all 3 trigger modes wanted eventually; UI lives in a new PROGRAMMING sub-tab). Losing the phase boundary/design rationale would mean re-deriving the "ad config doesn't exist, it's tag-matching" finding, the scope-cut decisions (no separate tagTaxonomy config — reused existing `collectAllTags()`-based autocomplete instead; `dayPartTemplate` field reserved on the profile but no UI yet; Phase 2's add-only-merge/no-channel-row-button cuts), and the Phase-3 "scheduled + create-new-channel forever-spawns-empty-channels" bug-before-it-shipped from scratch.

**Follow-up gap-fill batch shipped 2026-08-21** — after the user asked "what else could I improve", identified and closed the three real gaps left over from the phased build:
- **Bulk facet tagging** (`setup-panels.js` TITLES tab) — a collapsible "+ BULK FACETS" bar (mirrors the existing free-tag bulk bar) with genre/mood/era/contentType inputs; APPLY only touches a field the user actually filled in (so bulk-setting genre for 40 files doesn't also stamp a blank era on them), CLEAR resets facets only (free TAGS field is left alone, same "facets only ever add to tags" asymmetry as the per-row editor). This was flagged as the highest-leverage gap since a real boot test found the whole engine matching 0 of 1921 files — nothing was tagged yet, and one-row-at-a-time tagging doesn't scale to a real library.
- **`contentPoolScope.tags` UI** — a tag-style input in the profile editor ("CONTENT MUST CARRY ONE OF THESE TAGS"), wired to the data field that already existed but had no control.
- **`dayPartTemplate` UI + engine** — the biggest addition. `freshDayPartSlot()` (channels.js: `{id, label, startHour, endHour, genre[], contentType}`) plus a collapsible "ADVANCED: DAY-PART TEMPLATE" slot-list editor (add/remove rows, hour-range selects, label, content-type override, genre override). Engine side: `buildDayPartPlan`/`buildDayPartSlotPlan` (curation.js) score each slot independently (profile seeds narrowed by the slot's own genre/contentType via `slotThemeSeeds`, era/mood always inherit), slots get first pick of the candidate pool and claim their files before the flat plan runs so nothing repeats across slots or the base rotation. A populated dayPartTemplate produces real `ch.blocks[]` entries (`freshBlock('dayOfWeek')` shape, `days: []` = every day) tagged with an extra `curationSlotId` marker field so a later re-curate finds and extends the *same* block (add-only, matching Phase 2's channel-file merge) instead of duplicating it.
- **Real layout bug caught and fixed during boot-testing, not just a logic bug:** the new "+ ADD SLOT" button rendered full-card-width because `.daypart-slot-list` is a flex column (default `align-items: stretch`) — fixed with `align-self: flex-start` on the button. Caught by actually looking at the screenshot, not just checking that the click handlers fired.
- Verified live via CDP against the real 12-channel/1921-file library: candidate-pool math confirmed exactly right (1921 − 139 already-in-CH6 − 20 claimed-by-the-day-part-slot = 1762 scanned, exact match), preview correctly showed "+ NEW BLOCK — Test Morning Block: 20 file(s)" alongside the flat-plan diff, bulk facets toggle/inputs rendered correctly, zero console errors. Synced to `retro-cable-box-foss` and boot-verified there too, including the alignSelf fix.

**UI spacing/usability pass shipped same day (2026-08-21):** the AUTO-CURATE editor/preview cards had a real padding bug — they're raw `.interstitial-card` divs with no `.interstitial-card-summary`/`-body` wrapper (unlike every other pool/preset card in the app), so fields sat almost flush against the card border. Fixed with a new `.autocurate-card-body` class (`display:flex; flex-direction:column; gap:14px; padding:14px 16px`) applied to both cards, plus `#autocurate-root { display:flex; flex-direction:column; gap:16px }` for consistent spacing between the profile list/+NEW PROFILE/editor/preview blocks. Also split the editor's 11-field flat grid into 4 labeled sections (THEME SEEDS / CONTENT POOL / AD PRESET & BUMPERS / AUTOMATION, `.autocurate-section-label`) since it had grown past scannable-as-one-block size across the phases. **Same stretch bug caught proactively 3 times**: turning a container into `display:flex;flex-direction:column` makes every lone (non-row) button inside it stretch to full width by default (`align-items:stretch`) — hit this with "+ ADD SLOT" (caught via screenshot in the original day-part work), then pre-emptively fixed the same pattern on `advancedToggleBtn` and the root's `+ NEW PROFILE` button before it ever shipped broken, once the pattern was recognized. Also gave the TITLES tab's bulk-facets bar a cyan left-border accent (`.titles-bulk-bar-facets`) so it doesn't visually blend into the always-visible bulk bar above it. Verified via CDP screenshot comparison (before/after) and a DOM width sanity check confirming no button was stretched; synced to `retro-cable-box-foss` and boot-verified there too.

**Tag Taxonomy manager shipped same day (2026-08-21)**, a new sixth PROGRAMMING sub-tab (TAG TAXONOMY, after AUTO-CURATE). Two halves:
- `S.config.tagTaxonomy = {genres:[], eras:[], moods:[]}` (defaulted in `applyConfigDefaults`, `app.js`) — a curated per-category vocabulary the user builds up (3 chip-list editors, add/remove), which `collectAllTags()` (`setup-util.js`) now also folds into autocomplete suggestions everywhere, so a pre-declared-but-not-yet-used tag still shows up while typing. Deliberately no `contentTypes` category — that facet is already a fixed 5-value enum via `<select>` everywhere it's edited (TITLES facets, day-part slots), not a free-text tag needing curation.
- A new data module `renderer/js/tagtaxonomy.js` — `collectTagUsage()` (every distinct tag in use anywhere, with a count and which categories it's promoted into) plus `renameTagEverywhere(old, new)`/`removeTagEverywhere(tag)`, which walk **every** free-text tag location box-wide: file tags/facets (genre/mood arrays, era scalar) on both channel files and block files, interstitial pool `contentTags`, ad preset `contentTags`, every curation profile's `themeSeeds`/`bumperStyleTags`/`contentPoolScope.tags`/`dayPartTemplate[].genre`, and the taxonomy's own category lists — rename merges/dedupes into the target array rather than creating a duplicate. The UI (`setup-tagtaxonomy.js`) exposes this as a usage-report table (RENAME opens an inline form, no `window.prompt` — this app has no themed equivalent for that) plus REMOVE and per-row GENRES/ERAS/MOODS promote-toggle badges.
- **Real staleness bug found and fixed during boot-testing**: the generic PROGRAMMING sub-tab switcher (`setup-settings.js`) only toggles panel visibility, never re-renders — fine for every other sub-tab there (each only changes via its own edits), wrong for TAG TAXONOMY specifically since its whole point is reflecting tags set from a *different* tab (TITLES). A UI-driven test tagged a real file, switched tabs, and the usage report still showed the old snapshot even though the tag really had landed in `S.config`/disk — confirmed via a direct `collectTagUsage()` call in the same session that it *would* have shown correctly, proving the bug was purely "doesn't re-render on view," not a data bug. Fixed with a dedicated `click` listener on the TAG TAXONOMY sub-tab button itself calling `renderTagTaxonomyPanel()`, layered on top of (not replacing) the generic toggle handler.
- Verified two ways: (1) the rename/remove/dedupe logic directly against a fully synthetic scratch channel (`S.config.channels.push()`'d, exercised via dynamically-imported real module functions, then popped back out before the process exited — confirmed a two-location "scifi" correctly merged into an existing "sci-fi" with no duplicate, and cleanly removed a genuinely-unwanted tag), so no real library data was ever at risk; (2) the UI live via CDP against the real 12-channel/1921-file library (real usage counts rendered correctly — e.g. an existing "spongebob" tag showing 277 uses — confirming those real pre-existing tags predate this session's testing entirely and aren't test artifacts). Synced to `retro-cable-box-foss`, boot-verified there too.

**Auto-tag suggestions shipped same day (2026-08-21)** — `suggestFacetsFromPath(fullPath)` (`util.js`, alongside `guessCleanTitle`/`stripReleaseTags`) guesses genre/era/contentType purely from a file's own path: a plausible release year (1930-2029) anywhere in the path → decade era; `S01E02`/`1x02`/"season"/"episode" → contentType 'show'; an explicit "Movie(s)" folder → 'movie'; a modest generic-word genre dictionary (cartoon/comedy/horror/documentary/holiday/etc. — deliberately no hardcoded franchise/IP names). Wired into TITLES as a new "SUGGEST FACETS" bulk button next to the existing "STRIP RELEASE TAGS". **The user explicitly required this be additive, not replacing manual tagging** — it only ever fills a facet field that's currently empty on a given file, skips a file where every relevant facet is already set, and every suggestion lands in the exact same per-file FACETS editor a hand-typed value would, fully reviewable/overridable afterward. Verified two ways against the real library: a read-only pure-function pass over 400 real file paths (333 got at least one suggestion, zero mutation), and a live UI click-through on CH6's real 139 files (all 139 correctly got contentType='show' + era='2000s' from the "The Office (2005)" folder name, with a few also picking up genre='holiday' from episode titles containing "Halloween") — restored from backup after since the UI path really does write to disk. Synced to `retro-cable-box-foss`, confirmed there too.

**How to apply:** The whole roadmap (Phase 1/2/3) plus all four follow-up batches (gap-fill, spacing/usability, tag taxonomy, auto-tag suggestions) is done — there's no more phased work queued unless the user asks for something new (e.g. a "pending review" queue mode as an alternative to auto-apply, or free-form interval hours). Remember the [[retro-cable-box-cdp-autosave-gotcha]] pattern when boot-testing: back up `userData/channels.json` first. A read-only test session leaves the config byte-identical; a test that calls `applyCurationProposal`/`runScheduledCuration` directly WILL mutate real `S.config` in memory and schedule a debounced disk write — either avoid killing the electron process for several seconds afterward so you can verify+restore the on-disk result, or (as done here) kill it fast enough that the debounce never fires, then verify via diff that it didn't. Also see [[retro-cable-box-foss-parity]] — this is core, so any further edits need syncing to `retro-cable-box-foss` the same way (raw file copy of the touched core files; the FOSS repo has no git commits yet, so there's no history to diff against, just copy and boot-verify).
