Shipped 2026-08-16: an opt-in setting (SETUP > AUDIO, "OVERLAY AUDIO ON OTHER CHANNELS") lets the YouTube channel's (`YOUTUBE_CH`, 93) audio keep playing continuously in the background when you tune to a different channel, instead of stopping — "background radio mode," confirmed via AskUserQuestion before building (mixing choice: independent volume slider `S.config.youtubeMusic.overlayVolume`, applies to all channels except YOUTUBE_CH itself).

**Why:** requested directly by the user. This is a genuine architectural fork from [[retro-cable-box-architecture-constraints]]'s "one `<video>` element for everything" rule — flagged and scoped explicitly (like the Spotify Connect and LAN-viewer exceptions already on file) rather than quietly bolted onto the shared `player` element, since true audio overlay needs two simultaneously-live playback pipelines.

**Implementation:** a new dedicated `<audio id="youtube-overlay-audio">` element (`youtubeOverlayAudioEl`, dom.js) — YouTube playback (`youtube-music.js`) now goes through this element exclusively, never `player`. `stopYoutubeIfPlaying()` (called on every tune-away, virtual.js's `hideVirtualChannels`) checks `S.config.youtubeMusic.overlayEnabled` and no-ops if a track is playing (leaves it running); `stopAll()` (the in-channel STOP button) always tears down regardless of overlay mode, via a shared `teardownYoutubePipeline()` helper. Volume/mute: `applyVolume()`/`applyMuteState()` (power.js) now also drive `youtubeOverlayAudioEl` — master volume × `overlayVolume`, independent of the channel/break-kind multipliers `player` uses. `powerOff()`/`powerOn()` pause/resume the overlay element (via `resumeYoutubeOverlayIfNeeded()`, youtube-music.js, which respects the user's own PAUSE button state rather than force-resuming).

**Real bug found and fixed during this work:** `S.endedHandler`/`S.errorHandler` (state.js) were a *single shared field pair* used by every playback path that touches `player` (content, party.js) — safe before this feature because only one pipeline was ever live at a time (YouTube always tore down on tune-away). Overlay mode breaks that assumption: tuning to a new channel while YouTube overlay audio is live called the new channel's own `player`-scoped handler setup, which overwrote `S.endedHandler`/`S.errorHandler` out from under the *unrelated* YouTube pipeline — silently leaking its old `ended`/`error` listeners on `youtubeOverlayAudioEl` (never removed, since the field no longer pointed at them) while the overlay's own teardown/restart logic silently no-op'd against the wrong handler reference. Fixed by giving the overlay element its own dedicated pair, `S.youtubeEndedHandler`/`S.youtubeErrorHandler` (state.js), never touched by any `player`-scoped code.
**How to apply:** any future feature that introduces a second simultaneously-live media element must audit for this class of bug — any `S.*Handler`/per-pipeline bookkeeping field that was written assuming "only one thing plays at a time" needs its own dedicated copy per element, not a shared field, the moment two pipelines can be live concurrently. Don't assume an existing single shared field is safe to reuse just because it "worked" under the old one-at-a-time model.

Verified via the project's standard CDP boot-test discipline (real config, `Page.bringToFront`, backup+diff+repair) — confirmed: overlay ON preserves `youtubeNowPlaying`/handler across a tune-away, overlay OFF still tears down exactly as before; volume math (`master × overlayVolume`) and mute propagate correctly; power-off pauses and power-on resumes (unless user-paused via the PAUSE button, which correctly stays paused through a power cycle).
