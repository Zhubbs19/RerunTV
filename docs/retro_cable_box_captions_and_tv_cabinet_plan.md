**Update (2026-08-21, same session): real user-reported alignment bug found + fixed after initial "verification" passed.** The user tried the cabinet in the real app and saw a small ~35%-scale video floating in the middle of the wood console with a big wood-colored gap around it, not filling the punched-hole cutout — despite the earlier CDP checks all passing. Root cause: `applyTvCabinet` used `crtContainer.clientWidth/clientHeight` (a PRE-transform, local-coordinate-space measurement) to size `#tv-cabinet` itself, but `#tv-cabinet` lives OUTSIDE `#display-frame` (a sibling, per its own design — see above) which can carry a `transform: scale(...)` from AUTO display mode's simulated-resolution feature (`--display-frame-transform`, display-mode.js). `clientWidth` ignores ancestor transforms entirely; `getBoundingClientRect()` reflects the real post-transform screen box. `#player` (a true descendant of `.crt`) correctly uses the pre-transform value for its own `position:absolute` math — that part was always right. `#tv-cabinet`, being a sibling instead, needed the post-transform screen-space box instead, and using the wrong one produced a real, large, reproducible misalignment (confirmed via CDP geometry measurement: cabinet came out 1.107x scaled instead of the declared 1.3x, with ~150-190px drift between the SVG's drawn hole and the actual video position) whenever AUTO display mode wasn't at 'native' resolution. **Fixed** by splitting `applyTvCabinet` to use `crtContainer.getBoundingClientRect()` specifically for `#tv-cabinet`'s own size/position, while keeping `clientWidth/clientHeight` for the `#player` safe-area/crop math unchanged. Re-verified via CDP geometry measurement (not just eyeballing): drift dropped from ~150-190px to ~10px (~1%, floating-point-level), and a screenshot confirmed the video now fills the cutout edge-to-edge correctly.

**Lesson worth generalizing** (candidate for [[retro-cable-box-architecture-constraints]]'s CSS-gotcha list): `clientWidth`/`clientHeight`/`offsetLeft`/`offsetTop` are LOCAL/pre-transform measurements (what a `position:absolute` CHILD of that element would use); `getBoundingClientRect()` is the real POST-transform SCREEN box. Any two elements that need to visually line up but sit on opposite sides of a transformed ancestor (one inside it, one outside/sibling) MUST NOT mix these two measurement types for the same geometry — pick post-transform (`getBoundingClientRect`) for anything positioned outside the transformed ancestor, pre-transform (`clientWidth`/local) for anything positioned as a child within it. The bug here passed an initial CDP check because that check only verified aspect-ratio math (which held regardless of the scale bug) and computed-style values (also blind to the mismatch) — never a real cross-element geometry comparison against actual rendered pixels — worth remembering that a pure "did the code run and set plausible-looking values" check can miss a visual alignment bug entirely; a geometry-vs-geometry comparison (or, this time, the user just looking at it) is what actually caught it.

## Update (2026-08-21, same session): TV cabinet mode — major architecture rework after a second real user bug report

After the coordinate-space fix above, the user tried it live and found a DIFFERENT real problem: the guide overlay (and by extension every other on-screen element — CRT effects, logo bug, channel entry, etc.) rendered at full `.crt` size, spilling out past the cabinet's wood frame, because only `#player` itself was being resized to the cutout — nothing else in `.crt` knew cabinet mode existed. User explicitly asked for a general fix ("does that make sense" → confirmed → "go ahead") plus two more asks mid-implementation: make it easy to add more cabinets, and the theme dropdown is getting too long (18 entries) — the dropdown-length and AUTO-resolution-integration asks are tracked as **separate follow-up work**, not done yet as of this note.

**New architecture (replaces everything in the "TV Cabinet mode" sections above):**
- New DOM wrapper `#crt-content` (`index.html`) now holds EVERYTHING that used to be a direct child of `.crt` — video, every CRT/VHS effect layer, the existing subtle `#tv-bezel`, guide overlay + guide grid, logo bug, every modal/overlay (PIN lock, party channel, effects, trivia, details, TV menu), `#crt-power-fx`. This is the entire fix: every one of those elements was already written as "fill my nearest positioned ancestor" — swap what that ancestor's box is, and all of them resize together for free, no per-element code anywhere else.
- `dom.js`'s `crtContainer` export is **renamed in meaning**, not just name: it now points at `.crt-content`, not `.crt` — every existing consumer (`applyTvBezel`, aspect-mode fitting) needed zero code changes, since they already just read `crtContainer.clientWidth/Height`. New `crtOuterEl` export = `.crt` itself (always full-size), used only by `applyTvCabinet` to compute the cutout target.
- `applyTvCabinet()` is now dramatically simpler — no args, no video-crop math, no `computeFitRect` calls at all. It just sets `#crt-content`'s inline left/top/width/height to `cabinet.screenRect` fractions of `crtOuterEl`'s real box (or resets to blank/inset:0 when inactive). Content-fitting (aspect mode, the old subtle border) is `applyTvBezel`'s job as always, now operating on whatever (possibly cabinet-shrunk) box `#crt-content` currently is — **fully decoupled**: cabinet mode only answers "how big/where is the screen," never "how does content fit it."
- **`applyTvCabinet()` MUST run before `applyTvBezel()`** at every call site (reversed from the first version) since it establishes `#crt-content`'s box that `applyTvBezel` then reads. Updated in playback.js (4 sites), app.js (3 sites + a resize-time call now unconditional, since cabinet sizing no longer depends on video dimensions), setup-settings.js's `tvCabinetModeEnabledEl` listener. Also added to **`themes.js`'s `applyTheme()`** itself — the single central place every theme-switch path already goes through — so cabinet mode reapplies correctly no matter which code path changed the theme, not just the one setup-screen dropdown.
- **`cabinetFrame`'s shape is now drastically simpler** for extensibility (the user's explicit ask): `{ image, screenRect: {x, y, width, height} }` — screenRect is WYSIWYG, literally the same 0-1 fractions used to draw the transparent hole in the SVG's own viewBox, no scale/aspect/safeArea fields, no inverse-fraction math. `#tv-cabinet` itself is now just `inset:0` matching `.crt`'s own box exactly (no more 1.3x bleed-outward scale trick) — the framing illusion comes entirely from `#crt-content` shrinking into the hole, not from the cabinet art being oversized.
- **All 6 existing cabinet SVGs were redrawn** with new, thinner-margin screenRect values (addressing the user's separate "too thick" complaint about the wood console specifically) — direct fractions now, not the old inverse-scale-derived coordinates: wood-console-70s `{0.08,0.08,0.64,0.64}`, uhf-public-access-80s `{0.08,0.14,0.66,0.62}`, vhs-retro-80s `{0.08,0.08,0.66,0.64}`, network-primetime-90s `{0.05,0.05,0.75,0.80}`, digital-satellite-2000s `{0.05,0.05,0.82,0.72}`, frutiger-aero `{0.025,0.025,0.90,0.85}`.

**CDP-verified thoroughly this time** (not just aspect math): `#crt-content`'s real rendered rect matched the expected screenRect-derived box with **0.0px drift** on every axis, `#tv-cabinet` exactly matched `.crt`'s own outer box, and — the actual regression being fixed — **the guide overlay's real rendered rect now provably fits entirely within `#crt-content`'s bounds** (checked geometrically, not eyeballed). Toggling cabinet mode off correctly restores full size and hides the cabinet. Zero console errors. A screenshot confirmed the visual result: thinner wood margin, video filling the cutout edge-to-edge.
