## Completed P1 hardening

Completed on 2026-08-24:

1. **LAN authentication and privacy.** Viewer and phone-remote access are off by default; Party LAN access follows the existing off-by-default Party enablement. Enabled services issue host-visible pairing links, exchange the short code for a process-lifetime random HttpOnly/SameSite session, accept bearer sessions for native clients, rate-limit reads and mutations per client, and track devices only after authentication. Discovery advertises only enabled viewer/remote ports. Viewer config is recursively credential-redacted and replaces filesystem/provider references with process-scoped HMAC ids; `/media` rejects raw paths and resolves only ids registered by the projected config.

2. **Permanent contract/smoke tests.** `npm test` now covers manifest entries, bundled seeding upgrades, third-party/built-in integrity transitions, preload-versus-browser-shim parity with an explicit host-only allowlist, awaited plugin registration before first tune, paired viewer renderer/plugin HTTP assets, rejection of raw viewer paths, LAN opt-in/pairing/rate limits, `viewNow()` time offsets, and `configGeneration` invalidation of `resolveActiveCommercials`. The deploy workflow runs the suite after `npm ci` and before packaging. Current result: 12/12 passing.

3. **Renderer plugin trust boundary.** ZIP installs now record a SHA-256 digest in a ledger outside plugin folders. Manually copied or later-modified third-party plugins have main, renderer, settings, and CSS entry points blocked until the exact digest is reviewed and trusted. The Plugins UI distinguishes built-in/digest-verified files, labels renderer access as full UI access, and explains that isolated `main.js` does not sandbox renderer modules or global CSS. The author guide recommends sandboxed iframes/Workers with narrow messaging for third-party UI that does not need direct DOM integration, and states honestly that digest verification detects change but is not author identity/signing.

## Completed P2 follow-up (2026-08-24)

### P2 — extensibility/refactor phase

4. **Settings schemas and migrations.** `registerPluginSettings` now accepts optional `schemaVersion`, deep defaults, validation, dotted sensitive paths, and source-version migration hooks while retaining custom render sections. Applied versions live in `pluginSettingsMeta`; updates validate before mutation, and the plugin context exposes a redacted settings snapshot for diagnostics/support output. The starter plugin and author guide demonstrate the contract, and the permanent tests exercise migration, defaults, validation, and redaction.

5. **Split high-churn modules by feature boundary.** Preview time/schedule rules moved to `setup-channel-preview.js`, backup management to `setup-backups.js`, provider recovery/polling to `playback-recovery.js`, and plugin settings composition to `setup-plugin-settings.js` with its CSS in `setup-plugin-settings.css`. These are feature-owned modules rather than generic utility buckets; preview calculations still receive the selected timestamp and settings writes still use the generation-aware save funnel.

6. **Generate the viewer bridge from one contract.** `api-contract.js` is now the canonical method/target descriptor and generates the LAN browser surface, failing immediately on missing or extra viewer methods. Electron's sandboxed preload cannot import local modules, so the permanent contract test enforces its exact surface against the same descriptor; viewer omissions must be explicitly marked host-only.

7. **Plugin failure UX.** Each settings section now renders behind its own exception boundary. A failure produces an inline card with plugin ID, entry point, section ID, error, retry action, and restart guidance while sibling sections remain usable.

Verification after P2: `node --check` passed for every changed JavaScript entry and `npm test` passed 13/13. Electron UI behavior remains to be checked in a launched app because the automated suite does not render the setup screen.

8. **Package identity.** `electron-builder` reports that the default Electron icon is used. Add platform icons and verify signing identity in CI/release evidence.

### Completed P3 — exhaustive UI/accessibility phase (2026-08-24)

The expanded live-DOM pass changed the emphasis of P3. The base Display/Audio controls are already 12px or larger in the launched app; the remaining tiny text is concentrated in the flow builder, tag taxonomy, and plugin rows. The largest control/label problem is breadth rather than a single screen: the expanded bumper pool alone renders 135 dropdown instances with 1,137 options, while several generated controls depend on proximity or placeholder text instead of a programmatic name.

1. **Readability and density.** Enforce a 12px floor for setup controls and metadata without enlarging display headings, make the primary setup navigation compact/sticky after scrolling, and retain responsive wrapping at narrow widths.

2. **Complete semantics.** Connect every primary/subtab/edit tab to a real `tabpanel` with `aria-controls`/`aria-labelledby`, keep `aria-selected` and `aria-expanded` synchronized, derive accessible names for generated inputs/selects that currently rely on adjacent text, and mark changing status/toast regions as live regions.

3. **Overlay focus management.** Treat the full guide, Details card, and TV menu as labelled modal dialogs: move focus in, contain it where appropriate, and restore focus to the invoking control on close.

4. **Horizontal-flow affordance.** Add a visible step count, persistent themed scrollbar, and edge cue to the show/ad flow canvas so progression is understandable without relying on a clipped card.

5. **Responsive plugin section layouts.** Extend the generic plugin settings contract with `stack`, `two-column`, and `wide` layout hints; use the responsive two-column hint for Party rather than adding a core Party-specific selector.

6. **Theme parity.** Give all 18 theme plugins explicit setup-navigation and horizontal-overflow tokens, and verify the updated settings surfaces under every theme. Light themes need their own opaque sticky-navigation treatment rather than inheriting a dark hardcoded color.

7. **Evidence and regression checks.** Regenerate the full screenshot/component set after P3, compare component counts/dropdowns/options, run syntax/tests, and retain both pre/post evidence.

P3 is complete. The post-change set in [`docs/ui-audit-2026-08-24/post-p3`](docs/ui-audit-2026-08-24/post-p3) contains 93 artifacts: every primary/subtab state, all 9 channel edit/Schedule states, 3 channel utility states, 5 plugin categories, all 15 plugin settings panels, all 20 expanded Help topics, and 19 setup-theme renders (the 18 bundled theme plugins plus core Digital Cable). The live report inventories 537 visible controls, 28 dropdowns, and 137 options in the normal menu states with **0 unlabeled controls, 0 clipped controls, and 0 text-bearing controls below 12px**. The expanded pre-P3 pool report remains the exhaustive repeating-record sample with 135 dropdown instances and 1,137 rendered options.

All 18 theme plugins now define `--setup-nav-bg` and `--setup-overflow-shadow`; a permanent contract test enforces that coverage. The live theme matrix checks paper/cell, dim-text/cell, and accent/deep-background token pairs. Three misses found by the matrix were corrected in Network Primetime, Cloud Guide, and Wood Console; all sampled normal-text pairs now meet or exceed 4.5:1. Light Frutiger Aero and Neo Brutalist use opaque light sticky-navigation tokens rather than inheriting dark chrome.

Live Electron assertions also passed for sticky positioning, primary/subtab `tab`/`tabpanel` relationships, polite live regions, Party's responsive two-column section, TV Menu focus containment/restoration, and Guide focus containment/restoration. `node --check` passed for every P3 JavaScript file and `npm test` passed 14/14.

This is a code-and-screenshot audit, not a certification. NVDA/VoiceOver, 200% zoom, high-contrast mode, and automated contrast/DOM scanning still need a manual accessibility session.
